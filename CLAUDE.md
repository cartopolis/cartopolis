# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Build commands

Scope builds to the crate you changed — avoid `cargo build` without `-p` unless you need an integration check.

```bash
# Type-check shared protocol types
cargo check -p cartopolis_core

# Type-check/check server only (no Bevy — fast)
cargo check -p cartopolis_simulator

# Type-check Bevy client
cargo check -p cartopolis

# Run the game client. There is one dev profile and it builds dependencies at
# opt-level 3, so this is already a playable framerate — no --profile flag.
cargo run -p cartopolis

# Run with fast incremental links via Bevy dynamic linking (local dev only, not for release)
cargo run -p cartopolis --features fast-dev

# Run the headless sim server
cargo run -p cartopolis_simulator

# Release build
cargo build -p cartopolis --release

# Android. The check is the CI gate and needs only the NDK's clang (a build
# script's `cc` runs at check time); the APK needs an SDK and a JDK too.
# `docs/notes/android-build.md` — and note the crate is *empty* off Android, so
# `cargo check --workspace` says nothing about it.
cargo check -p cartopolis_android --target aarch64-linux-android
crates/cartopolis_android/build-apk.sh          # → $CARGO_TARGET_DIR/android/cartopolis-arm64-v8a.apk
```

Unit tests live in `#[cfg(test)]` modules inside `cartopolis`, which is a lib target
plus a shim bin, so `cargo test -p cartopolis` links the rlib rather than rebuilding
the whole crate under `cfg(test)`. Note `cargo check`
does **not** compile `cfg(test)` code — the suite silently rotted through the egui 0.35
migration until someone ran it, so run the tests, not just a check, when touching egui
or the building geometry.

**Linker:** `.cargo/config.toml` uses `clang + lld` on Linux. If linking is slow, switch to `mold` (`fuse-ld=mold`).

**Never export `CARGO_TARGET_DIR` on the workstation.** sccache (wired as
`rustc-wrapper` in `~/.cargo/config.toml`) hashes that env var into its cache
key, so setting it silently zeroes build sharing between git worktrees — each
worktree builds into its default `target/` instead, in parallel, at ~85 % cache
hits. The container is the exception: it bakes one constant value for one shared
target dir. See `docs/notes/sccache-parallel-builds.md`.

**Git LFS is a build prerequisite, and its failure mode is silent.** `.gitattributes`
tracks binary assets by extension anywhere in the tree (models, images, fonts, audio,
`.mvt` fixtures), so a new asset needs no setup — but four of them are
`include_bytes!`-ed at *compile* time (the brand font in `systems::theme`, the app
icon, `assets/sky/bright_stars.bin`, the tile fixtures). Clone without `git lfs
install` and `cargo build` cheerfully embeds 130-byte pointer files: the font panics
in epaint, the icon doesn't decode, the fixture tests assert against garbage. Every
`actions/checkout` in `.forgejo/workflows/` sets `lfs: true` for the same reason —
add it to any new job.

### The documentation image set (`cargo shots`)

The README images are **data, not a manual ritual**: `docs/shots.toml` remembers
six named camera positions (name, `at = [lat, lng, alt]`, `look = [pitch, yaw]`,
plus per-shot `mode` / `time` / `fog` / `clouds` / `rain` / `ui` / `hide_ui`), and

```bash
cargo shots                      # all of them → docs/img/<name>.png
cargo shots --only globe,route   # a subset
```

regenerates the whole set in one headless launch. `cargo shots` is an alias for
`cargo run -p cartopolis -- --shots`, so every `--shot` flag
below still applies (`--csv`, `--dump-state`, `--size`, `--settle`). A manifest
run is the same harness: each preset owns its filename, its camera mode, the
panels it opens and the time of day it is shot in, and the metrics CSV gains a
`name` column so six rows aren't six anonymous viewpoints. The manifest also
pins `tile_url` — a scripted run never sees the server handshake that supplies
one, and the built-in fallback is the *raster* basemap, on which the `route`
preset renders "Routing needs a vector tile source" instead of a route
(`CARTO_TILE_URL` still overrides it). Unknown manifest keys
are a hard error (a typo'd `hide-ui` that silently did nothing would only show up
as a chrome-covered README image later). To add a view, fly there and use the dev
panel's **📋 Copy as preset** button — it puts a pasteable `[[shot]]` block on the
clipboard. The dev panel's numbered capture slots remain, but they are scratch
files now; the README links to the preset outputs.

### Scripted screenshots (`--shot`)

Answer "what does it actually look like from there?" without flying the camera by
hand (`crates/cartopolis/src/systems/dev/shot_harness.rs`):

```bash
# one frame, straight down from 180 km
cargo run -p cartopolis -- \
    --shot /tmp/shot.png --at 53.2194,6.5665,180000 --look=-90,0

# an altitude sweep in ONE launch → /tmp/sweep_0_60000m.png, /tmp/sweep_1_1000000m.png, …
cargo run -p cartopolis -- --shot /tmp/sweep.png \
    --at 53.2194,6.5665,60000 --at 53.2194,6.5665,1000000 --look=-90,0

# a 24-frame flythrough between two --at, with the ramp scalars logged to CSV
cargo run -p cartopolis -- --shot /tmp/fly.png \
    --at 53.2194,6.5665,2000 --at 53.2194,6.5665,4000000 --frames 24 \
    --look=-90,0 --csv /tmp/ramps.csv
```

`--look` takes `pitch,yaw` in degrees and pairs with `--at` by position (note the
`=`: clap reads a leading `-90` as a flag otherwise). Runs are **headless**: no
window is created at all (`WinitPlugin` is disabled and `ScheduleRunnerPlugin`
drives the frames), and the camera renders into an offscreen image. Nothing
appears on the desktop, no compositor can occlude — and blacken — a capture, and
a shot works over SSH or in CI with no `DISPLAY`/`WAYLAND_DISPLAY` at all.
Each shot waits for the tile streams to go quiet (`--settle`, capped by `--wait`)
instead of sleeping a fixed time, and logs a `shot state` line — altitude, tier,
near/far, globe entity/visible/rendered counts — which is what separates "black
image" from "black scene". The egui overlay is included (the HUD makes a shot
self-documenting); `--hide-ui` omits it. Scripted runs never read or write
`data/user.json`. Other flags: `--size WxH`, `--shot-mode free|earth`, and
`--time HOURS` / `--fog DENSITY` (seed the day-night and fog state — how the
lighting curves get A/B'd: `--time 6` for dawn, `--time 18 --fog 0` to tell a
washed-out sky apart from a washed-out fog).

**Sweeps and metrics (the transition/introspection layer).** Every capture also
measures a `ShotMetrics` — altitude, tier, the altitude-driven crossfade scalars
(`space_factor`, exposure, bloom, `globe_albedo`), near/far, and the globe mesh
tally — from one source into three sinks: the `shot state` log line (always),
`--csv PATH` (one row per capture), and `--dump-state PATH` (the full metrics as
JSON — a bare object for a single shot, an array for a sweep). A new inspectable
fact is one field on `ShotMetrics` (`shot_harness.rs`) and it appears in all three
at once — this is the "inspect the settled world from a shell without a recompile
per question" path. `--frames N` (needs ≥2 `--at`) interpolates N viewpoints along
the waypoint polyline (**altitude log-interpolated**, so samples aren't all bunched
in space; lat/lng/look linear) instead of one capture per `--at`; sweep PNGs are
index- **and** altitude-tagged (`fly_00_2000m.png`) so the filmstrip sorts in
flight order. Pair `--frames` with `--csv` to catch a **hard cut in a ramp**: a
jump between adjacent rows of the `space_factor` / `exposure` / `bloom` /
`globe_albedo` columns is a seam a single still can't reveal. The metrics report
*actual* camera state (e.g. the placed altitude after the teleport snaps it), not
the requested `--at` — which is the point.

**`--expect` turns the instrument into a gate.** `--expect 'settled==true'
--expect 'globe_rendered>0'` (quote them — `>` is a shell redirect) asserts any
`--dump-state` field on every capture and exits
non-zero when one doesn't hold, logging `shot expect failed` with the *measured*
value beside it. It is repeatable, operators are `>= <= == != > <`, booleans are
`true`/`false`, and an **unknown key is a hard error at startup** (same rule as an
unknown manifest key — a typo'd assertion that quietly holds is worse than none,
because a green run then claims something nobody checked). Two deliberate
choices: a failure does not abort the run, so the remaining viewpoints are still
captured and a red CI job hands back the PNG and the metrics that explain it; and
`==` is exact, so assert a float with `>=`/`<=` unless you mean the bit pattern.
This is what the `scene-smoke` CI job is built on — and note what it may *not*
assert: on the CI runner's software rasteriser, colour, exposure, bloom and
lighting are not evidence (`docs/notes/headless-shots-software-renderer.md`), so
gate on geometry, placement and visibility.

With no window, `--size` *is* the screen: `resources::HeadlessSurface` stands in
for the primary `Window` so egui has something to lay out and scissor against
(the overlay renders into the capture as usual) and the globe LOD keeps its
screen-space split threshold honest. Anything that reads `Query<&Window>` must
fall back to it or degrade gracefully — a scissor rect that doesn't match the
render target fails wgpu validation, and Bevy answers that by quitting the run
silently, mid-stream, before the first capture.

Startup switches for bisecting a render problem, each removing one layer:
`CARTO_NO_ATMOSPHERE=1`, `CARTO_NO_HAZE=1`, `CARTO_NO_ENVMAP=1`,
`CARTO_NO_OCEAN=1` (the globe's ocean split — see `systems/map/globe_ocean.rs`).

## Architecture

The account-admin GUI is **not in this repo**: it is
[`jeroen/cartopy`](https://code.garage44.eu/jeroen/cartopy), a Preact + deepsignal app deployed to
`web.cartopolis.org` on every push to its own `main`. It talks to this
simulator's `/api/admin` surface and nothing else, which is the whole reason it
can live apart. The seam to know about is `src/types.ts` over there — a
hand-written description of what `auth::AccountRow` serialises here, and with the
two in separate repositories nothing but a person keeps them in step. Change an
account field and change it there too. `docs/notes/hosted-simulator.md` has the
deployment.

This is a **Cargo workspace** with six crates:

| Crate | Role | Notable deps |
|-------|------|-------------|
| `cartopolis_core` | Shared protocol types, `NetMessage`, tile/coordinate math | `serde`, `postcard`, `glam` |
| `cartopolis_geo` (`crates/geo`) | Bevy-free map geodata: MVT decode/raster, road classes, tree scatter, the routing graph. ~6,900 lines and 60 tests that used to be recompiled and relinked behind the Bevy binary. **Nothing here may depend on `bevy`** — if a type needs a `Component` it belongs in `cartopolis`, and the pure part it wraps belongs here. Re-exported by `systems/mod.rs`, so client code still writes `systems::vector_tiles`. | `mvt-reader`, `tiny-skia`, `earcutr`, `image` — **no Bevy** |
| `simulator` | Headless TCP simulation server; SQLite authority; tick loop | `tokio`, `rusqlite`, `refinery` — **no Bevy** |
| `cartopolis` | Bevy 0.19 client; rendering, ECS systems, UI | Bevy 0.19 + `big_space` (path dep), `egui` 0.35 |
| `cartopolis_android` | The Android app: a `cdylib` owning `android_main`, plus `AndroidManifest.xml` and `build-apk.sh`. **Both its dependencies are target-gated**, so off Android the crate is empty — 8.4 s and a 4.3 MB artifact in a workspace build, not the second full static link of Bevy that a `cdylib` on `cartopolis`'s own `[lib]` would cost. "Empty" is not free and cannot be: a cdylib links std regardless. It also means `cargo check --workspace` proves nothing about the crate, which is why CI checks it for `aarch64-linux-android` separately. `docs/notes/android-build.md` | Bevy 0.19 + `cartopolis`, on `cfg(target_os = "android")` only |
| `big_space` | **Vendored fork** of `big_space` 0.10 ported to Bevy 0.19 (floating-origin transform propagation, ADR-019). Upstream tops out at Bevy 0.18, so we keep a copy under `crates/big_space` and advance it on each Bevy bump — re-sync the vendored transform-propagation code (`bevy_compat.rs`) against Bevy when upgrading. | Bevy sub-crates |

### Client (`cartopolis`) — Bevy ECS layout

- **`components.rs`** — Bevy `Component` types: `Region`, `Prim`, `Avatar`, `RemoteAvatar`, `Selected`, etc.
- **`resources.rs`** — Bevy `Resource` types: `GameState`, `AvatarState`, `CameraState`, `ContextMenuState`, `EditDialogState`, `MouseState`, `OsmTileUrlTemplate`, `ConnectAddr`
- **`systems/`** — one file per concern, all registered in `lib.rs`. The files are
  grouped into folders (`geo` `map` `nav` `player` `gui` `net` `dev` — see
  `systems/mod.rs`), but **the folders are not the import path**: `systems/mod.rs`
  re-exports every module flat, so it stays `systems::water`, never
  `systems::map::water`. That is deliberate — `lib.rs` reaches most systems through
  `use systems::*`, and regrouping must not become a 151-call-site edit. Adding a
  system means a `pub mod` in the group's `mod.rs` plus a name in the `pub use`
  list. The group is `gui`, not `ui`, because `systems::ui` is one of the panels.
  - `avatar` — movement, animation, remote avatar interpolation
  - `camera` / `free_camera` — orbit camera, mode toggle
  - `collision` — avatar↔building collision (footprint index; walk-block + teleport eject)
  - `network` — TCP connection to `simulator`, snapshot apply, intent send
  - `rendering` — spawn/update Bevy meshes for regions and prims
  - `tile_loader` — async OSM tile fetch → region texture
  - `picking` — raycasting for prim selection
  - `bookmarks` / `place_pins` — saved places as a **directory tree** (nested folders, each with a colour, drag-and-dropped) in the Places panel, and the matching teardrop map pins painted over the map in their folder's colour
  - `ui` — egui context menu + prim edit dialog
  - `theme` — **the only place UI colour, spacing and type live.** The palette is read off the logo (slate blue `#1B2830`–`#2e424e`, accent orange `#FD6012`, amber `#FD9212`, cream `#F2EFEA`); `theme::install` is called from `EguiManager::default` *before the first pass*, which is what binds the brand font family in time for the splash's wordmark. New UI code takes its colours from these constants, its box-over-the-map frame from `theme::overlay_frame()` and its title bar from `theme::panel_header()` — a fresh `Color32::from_rgb` in a panel is how the chrome drifted last time, and six hand-rolled `heading` + `button("✕")` rows is how every panel ended up with a tofu box for a close button (`✕` is not in the bundled font; `theme::close_button` paints its cross from two line segments instead). A panel's glyph and name come from `RightPanel::icons()` / `label()`, so the dock disc, the menu entry and the header medallion are one table. Keep `index.html`'s loader CSS in step with it (same brand, drawn before any Rust exists). Contrast is unit-tested, including the non-obvious one: egui derives `RichText::strong()`'s colour from `widgets.active.fg_stroke`, so the pressed-button state and every bold value in the app are the same knob.
  - `gizmo` — transform gizmo toolbar and drag interaction
  - `egui_manager` — custom `EguiPlugin` (wraps `egui-wgpu`); renders egui as the `egui_pass` **system** in the `Core3d` render schedule (Bevy 0.19's schedule-based render graph replaced the old `ViewNode`/render-graph API), drawing onto the post-upscaling sRGB output. Panels use a shared root `Ui` (egui 0.35 shows panels inside a `Ui`, not the `Context`).

**Run modes (`systems::session`, ADR-016/031): there are exactly two.** **Online** is server-authoritative — the avatar and prims live in `simulator` and are replicated over the wire; the client sends `ClientIntent` (a walk-velocity wish + fly flags) and applies `WorldSnapshot`s; `--connect <host:port>` pins the launch to a server. **Offline** (`--offline`, implied by `--shot`) runs no sim at all — single user, no auth, no world persistence; only the streamed OSM/3DBAG map and a local avatar move under client control. The third mode this tree used to have — **solo**, an in-process sim behind a `solo` cargo feature — was removed 2026-08-21: it was "online to yourself" wearing a mode of its own, plus a SQLite neither wasm nor Android could compile. The dev loop is `cargo run -p cartopolis_simulator` (`--create-admin dev` + `CARTO_ADMIN_PASSWORD` once) and a sign-in to `127.0.0.1:4747`; the simulator crate remains a dev-dependency of the client so the loopback tests boot the real thing, and an old `user.json` remembering `"solo"` reads as offline (`SessionKind`'s `#[serde(other)]`). There is **no client-side database** anymore: the old local-SQLite path (`db/`, `systems/database.rs`, the `Database` resource) was removed. Persistence and world authority live in `simulator` (`data/world.db`).

**The mode is switched at runtime, not chosen at launch** (`systems/net/session.rs`, `systems/gui/login_screen.rs`, `docs/notes/session-modes.md`). Offline is *the absence of `OnlineSession`* — every online system was already `Option<Res<…>>`-guarded — so the sim is an extension of the offline viewer that can be entered and left while the app runs. `SessionState` holds the mode, a status and a `request` field the sign-in screen (☰ ▸ Sign in…) and startup both write; `session::drive_session` takes it, and `connect`/`teardown` are written as an exact pair — dropping `OnlineSession` closes the socket but leaves the server's regions, prims and remote avatars standing, which is a half-online client. Startup is just the first request: a flag wins (an instruction for this launch, never written back), otherwise the remembered session in `user.json` decides, and its default is **offline**-with-auto-enter — everybody starts on the map with nothing to sign in to, and the card (☰ ▸ Sign in…) asks one question, a server. The local avatar entity is never despawned — its offline movement path takes over the frame the session goes.

**The web build is no longer viewer-only.** It was, and `can_simulate()` returned `false` there to say so; it now has a WebSocket carrier and returns `true` everywhere. In the Server field, an empty address means **this page's own origin** (`network::ws_url`), which is what the deployed client uses — that function is in `network.rs` rather than the wasm-only `ws_transport.rs` so it is compiled and unit-tested on the native lane.

### Server (`simulator`) — async Tokio

- `config.rs` — layered config: `cartopolis.toml` → env (`CARTO_*`) → CLI flags
- `db.rs` — SQLite open, `refinery` migrations, world load
- `net.rs` — TCP `handle_connection`, tick loop, `WorldSnapshot` broadcast
- `state.rs` — `SimWorld`: authoritative avatar + prim state, AoI filtering

### Shared (`cartopolis_core`)

- `protocol.rs` — `NetMessage` enum, `encode/decode_app_frame`, and `PROTOCOL_HISTORY`: the wire changelog, one `ProtocolRevision { version, adr, summary }` per revision. `PROTOCOL_VERSION` is *derived* from its last entry, so **bumping the version means appending a row** — don't write the number anywhere else (three docs drifted to "currently 8" while the wire was at 11). A unit test enforces the run stays gapless.
- `world.rs` — `TileKey`, lat/lng ↔ tile math, `REGION_SIZE_METERS`
- `yaw.rs` — angle helpers for avatar direction continuity

**Wire format (ADR-008–009):** TCP length-delimited frames, little-endian `u32` length; frame body = an 8-byte header (`APP_HEADER_LEN`) of `protocol_version` (u16 LE) + `message_kind` (u16 LE) + `request_id` (u32 LE), then the postcard payload.

**Two carriers, one wire.** A browser cannot open a TCP socket, so the same frame *body* also travels as one **binary WebSocket message** — `cartopolis_simulator::http` on the server, `systems::ws_transport` (wasm) and `network::Wire` (native) on the client. Only the framing differs, so a new carrier is **not** a protocol revision and `PROTOCOL_HISTORY` gains no row for one. `net::handle_connection` is generic over `net::FrameTransport` (a `Stream` of frames plus a `Sink` of them) precisely so there is one 700-line connection loop rather than two that must stay identical with nothing to say when they stop being. `tests/http_surface.rs` pins the consequence: a session token minted over WebSocket authenticates over TCP.

**Every build reaches a remote sim over TLS, and the address decides** (`network::resolve_target`). A bare hostname resolves to `wss://host/ws` — so the *easy* thing to type is the encrypted one, which is the whole design: the wire carries a password and then a session token, and this used to cross a public plaintext port in the clear. Loopback (`127.0.0.1`, `localhost`, `::1`) stays plain TCP, because that is a dev sim on this machine and TLS to yourself is a self-signed cert plus a disabled verifier — the appearance of security over traffic that never touches a network. `tcp://` and `ws://` opt out explicitly, for a private CA or a LAN dev sim; nobody reaches either by typing a hostname, and `a_remote_address_is_always_encrypted` fails if that ever stops being true. Two dependency constraints follow and are not preferences: **rustls, not native-tls** (native-tls is OpenSSL, and the CI Android lane has only the NDK's clang), and rustls 0.23 **panics at the first connection** unless a `CryptoProvider` is installed — it compiles fine and dies when somebody signs in, so `network::install_crypto_provider` does it explicitly.

**The user-safety surface is split the same way, and the server is what refuses**
(`docs/notes/user-safety.md`). A filter, a report path, a block and published
contact details are what a store requires of an app carrying user-generated
content, and this one has chat, voice, shared prims and author scripts. Filing a
report and setting a block are *player* actions, so they are on the wire
(`SetBlocked` / `BlockedList` / `ReportUser` / `ReportAck`, protocol 16), as is
deleting your own account (`DeleteAccount`, which re-checks the password because
a session token can be a remembered one on somebody else's device). Triaging a
report is an operator action, so it is on `/api/admin/reports`. Every refusal is
enforced in `ChatHub`'s fan-out and in `net.rs`, never in the panel that draws
it — a client can be rewritten, so a block applied in the UI is not a block. The
one thing the client decides for itself is hiding lines that had *already*
arrived when the block was made, which the server cannot retract.

**Account management is HTTP, not the wire** (`crates/simulator/src/http.rs`, `--http-listen`). Operator actions are deliberately off `NetMessage`: putting them there would run an authorisation decision through the same path as a movement intent and would move every client's protocol version whenever the *admin* surface changed. What the two surfaces share is the account table and the session map, which is the point — an admin signs in with an ordinary account. Two consequences worth knowing: **`disabled = 1` gates the next handshake, not the current session** (`Sessions` is keyed by token with no principal index), and the **last enabled admin cannot be demoted, disabled or deleted** — a running server with no admin is only repairable with shell access, via `simulator --create-admin <user>` and `CARTO_ADMIN_PASSWORD`.

## Known issues / workarounds

- **All persistence goes through `platform::storage`, and on the web that is IndexedDB** (`docs/notes/web-persistence.md`). Path-shaped keys in two namespaces: `Cache` (tiles, 3DBAG, Overpass, transit — evictable) and `Data` (`user.json`, place photos — the first write asks `navigator.storage.persist()`). Natively those are `cache_root()` and `app_data_root()`, i.e. exactly where the files always were. **Until 2026-08-13 the web build persisted nothing at all** — `user.json` went through `std::fs`, every write failed silently, and every setting and bookmark was lost on reload. The thing that makes one code path work on both is that no browser has a synchronous read on the main thread (OPFS's sync handles are worker-only), so `run()` on wasm *preloads* the keys that must be readable synchronously — `user.json` and the photo thumbnails — before the `App` is built, and every startup path downstream is then native-shaped. `read_now` answers `Ready`/`Loading`/`Missing`, and **collapsing `Loading` into `Missing` is a bug that never recovers**: a caller caching "not there" the way it would cache a filesystem miss keeps that answer forever.
- **egui paints floating `Area`s *above* panels, so a world-anchored overlay has to cull itself to the map area.** Panels live on the bottom-most background layer and even an `Order::Background` `Area` draws over them (the HUD compass/status box work around it by disappearing while a right panel is open). The place pins can't disappear — they're the feature — so `place_pins::render_place_pins` culls every pin against `EguiManager::ui_mut().available_rect_before_wrap()`, which is the *leftover* space of the shared root `Ui` and therefore exactly the map. That only holds if the system runs **after every panel system** (it's ordered last, in lib.rs Phase 8); run it earlier and it sees the full viewport and paints pins over the Places list. Culling — not just `set_clip_rect` — is what matters, because a clipped-away pin would still be an interactive `Area` stealing clicks meant for the panel behind it.
- **Every system that draws a panel into the shared root `Ui` must be *totally* ordered against the others** — and the failure when one isn't is not a visual swap, it is dead clicks. The panels share the single `Background` layer, so if Bevy is free to run two of them in either order, on the frames where one composes first its widgets sit *over* the other's and win egui's hit test. The covered checkbox then reports `contains_pointer() == false` while its rect contains the pointer, its clip contains the pointer, and `layer_id_at` still answers `Background` — because the contest is *within* a layer, invisible to every layer-level diagnostic. It reads as "the checkbox needs several clicks" (each press is a coin flip) and it will not reproduce in a single-panel test. The chain is `menu_bar → ai → layers → bookmarks → route → chat → appearance → place_pins`, and since 2026-08-06 it is **one `.chain()` tuple in `lib.rs` Phase 7b** rather than a dozen `.after()` links scattered over two `add_systems` calls. **Add a panel by putting it in that tuple** — ordering is then structural, and a panel registered anywhere else is visibly not in the chain. `place_pins` must stay last for the separate reason below. The total order costs no parallelism: every one of these takes `ResMut<EguiManager>`, so Bevy already runs them one at a time and ordering only decides *which* order. `chat` and `appearance` were left out when the bottom bar grew them (fixed 2026-07-31) — note `chat::render_chat_panel` draws *both* a bar `Area` and a root-`Ui` panel, so "it's an overlay" is not a reason to leave it out.
- **Street names are world geometry, not an overlay** (`systems::street_labels`, Map ▸ Street labels). They are textured quads lying in the road surface — CPU-rasterised with `fontdue` over egui's embedded font, cached per name, one rung of the depth-bias ladder above the route line. A screen-space version was built first and rejected on sight: text that keeps its size while the city changes scale under it, and that draws over the buildings in front of it, reads as a note stuck to the glass. Three things follow and are load-bearing: placement is **view-independent** (world footprints, "is the street long enough in metres to carry the name") so it cannot flicker and only re-runs when the cells, the size band or the camera *heading* change; the size **steps** through `HEIGHT_BANDS` rather than ramping, because a continuous size would re-place every label every frame of a climb; and the baseline is laid to read left-to-right for the current heading, so the names flip when you swing the camera round. `docs/notes/map-labels.md` has the rest.
- **An egui long press fires `clicked()` as well as opening the context menu.** A saved place's actions live in `Response::context_menu` rather than in the row (the thumbnail needed the width, and four finger-sized buttons left no room for the name on a phone). egui reaches that menu from touch on its own — `secondary_clicked` is true for a long touch, and this client already feeds it real `Event::Touch`es — but its press-and-hold handler *also* synthesises a click, so `place_row` guards the jump with `!response.long_touched()`. Without that, a long press opens the menu and flies the camera to the place behind it. Any clickable widget that grows a menu needs the same guard. Photos themselves are `docs/notes/place-photos.md`: two JPEGs per place in the **Data** namespace of `platform::storage` with only the stem in `user.json`, one capture seam (`platform::photo`) over a desktop file dialog, a browser `capture="environment"` input and — because `android-activity` surfaces no activity result and the APK has no dex — an Android camera intent watched through the MediaStore row it writes into. That Android arm compiles for aarch64 and **has never run on a device**.
- **`Ui::dnd_drag_source` and a `TextEdit` in the same row fight over the press.** The drag source lays a `Sense::drag()` widget over the *whole* row after its contents, and a `TextEdit` senses drag too (that is how it selects text) — the row's, being registered last, wins. Clicking into an inline rename field started dragging the row instead and the field never held the keyboard. `bookmarks::rename_row` therefore draws a row being renamed as a plain row with no drag source at all. Buttons inside a drag source are fine: egui resolves `hits.click` and `hits.drag` separately, so a click still reaches the button. Give the field an explicit `Id` too (`rename_field`) — its auto-id shifts when the row swaps a label for a field, and a field whose id changes between frames loses focus on the frame it gains it.
- **Atmosphere is Bevy 0.19's built-in `bevy_pbr` atmosphere** (not `bevy_atmosphere`, which was dropped). It's planetary-scale, so `free_camera::setup_camera` spawns it on a **planet-centered entity** 6,360 km below the local ground (surface at `y = 0`). The camera carries `AtmosphereSettings` + `AtmosphereEnvironmentMapLight` + a physical `Exposure`, the sun runs at `RAW_SUNLIGHT`, and `apply_day_night_cycle` adapts exposure by time of day. **Space tier:** the atmosphere stays on in both tiers; `globe::update_globe_visibility` switches the camera's `AtmosphereSettings` to `AtmosphereMode::Raymarched` (reduced `sky_max_samples`) above `GLOBE_SHOW_ALT` and back to `LookupTexture` below, and drops `AtmosphereEnvironmentMapLight` in space. This only works because `globe::update_atmosphere_origin` moves the planet-centered entity each frame to Earth's true centre in render coordinates: the camera is the big_space floating origin (`GlobalTransform` ≈ 0 at any real altitude), so the old fixed `(0, −R, 0)` placement made bevy_pbr always see a ground-level camera — "Raymarched from space" then integrated a *surface sky dome* over the whole screen (black/washed globe, wasted GPU), which was misdiagnosed as Raymarched being unusable from orbit. Escape hatch: `globe::SPACE_ATMOSPHERE = false` disables the atmosphere in space by stripping the planet entity's `Atmosphere` component (tagged `globe::PlanetAtmosphere`, which keeps a copy for restore). Stripping that component is the **only** real off-switch: bevy_pbr's `extract_atmosphere` inserts `ExtractedAtmosphere`/`GpuAtmosphereSettings` onto the camera's *retained* render-world entity and only removes them when **zero** `Atmosphere` entities exist — removing `AtmosphereSettings` from the camera just drops it out of the extract query, leaving the stale render-world components (and every atmosphere pass gating on them) running forever (an earlier fix did exactly that and was a render-world no-op). The globe-tier near/far override lives in `free_camera::camera_controls` **after** the mode match so it applies in every camera mode (a far plane stuck at 200 km otherwise clips the whole globe → black screen when high).
- **Not every GPU can run that atmosphere, and the ones that can't get `systems::sky_dome`** (`docs/notes/sky-without-an-atmosphere.md`). Bevy 0.19 bakes each `ScatteringMedium` into `Rgba32Float` LUTs read through a *filtering* sampler, which wgpu allows only on an adapter reporting `FLOAT32_FILTERABLE` — desktop GPUs and lavapipe do, a great many mobile ones (the Adreno 619 in a Fairphone 4) do not, and there the bind group fails validation and takes the app down. So `setup_camera` decides the sky once, records it as `SkyMode`, and three places downstream read that one answer. The fallback is an analytic single-scattering shell: same Rayleigh/aerosol coefficients as `utils::sun`, so the sky reddens with the sun, the fog and the clouds rather than beside them; explicit twilight and night floors because single scattering has no light after sunset; altitude by barometric column, hidden below `GLOBE_SHOW_ALT` because it is a flat-earth sky. Opaque and depth-write-off *on purpose* — every other sky shell is camera-centred and ties in the transparent distance sort, and the dome must land under all of them. `CARTO_NO_ATMOSPHERE` still means **no sky at all** (it is a bisecting switch, and since the render toggles left the dev panel it is the *only* way to get `SkyMode::None`); `CARTO_SKY_DOME=1` forces the fallback anywhere, which is how you see the phone's sky without the phone. The user-facing half is **Settings ▸ Graphics ▸ Sky** (`AppPrefs::sky`, Automatic/Full/Simple) — not redundant with the flag but the other side of it: a flag is per-launch and reaches a scripted capture, the setting persists and is the only one of the two a phone can reach. Asking for Simple always works; asking for Full still has to pass `FLOAT32_FILTERABLE`, because refusing beats the bind-group validation failure that takes the app down.
- **The atmosphere is fed by the sun light — don't pre-extinct it.** bevy_pbr scatters the sun `DirectionalLight`'s *colour and illuminance* and applies its own air-mass extinction on top. `sky::sun_light` also models extinction (`utils::sun`, for the surface lighting bevy does *not* attenuate), so the two compound: at the full Kasten–Young curve dawn kept 9% of the beam, the atmosphere took its cut of that, and sunrise rendered as a near-black maroon sky over a maroon city. `SUN_EXTINCTION_SOFTNESS` bends only the large-air-mass end of our curve, `SUN_COLOR_SATURATION` keeps the hue mild, and `TWILIGHT_EXPOSURE_LIFT` supplies the eye adaptation that makes twilight *read* bright. Whenever the sun light changes, check the sky too — every knob moves both.
- **Sky props are viewer-centred shells sized for the ground** — the star field (150 km) and the moon disc (140 km). From orbit that is *nearer than the planet*: stars blended over the Earth disc and the moon quad hung in front of it. `GlobeState::sky_shell_radius` returns the space radius (past the far limb, inside the far plane `camera_controls` sets) and `update_star_sky` / `update_moon` scale the whole transform uniformly, which preserves every angular size. The star shader also takes a **space flag** (`params.z`): its horizon cut (`dir.y`, the *anchor's* up) hid the entire field from orbit, because looking down at the globe every star on screen is below that horizon — the flag drops the cut along with the air extinction and twinkle. Star brightness is likewise ungated from the local clock in space; it was the day/night fade that left the globe in a black void at noon.
- **The sun disk is Bevy's procedural one** (`bevy_light::SunDisk` on the sun `DirectionalLight`, drawn by the atmosphere's sky pass, so it needs no geometry and works raymarched from orbit). It's on by default at Earth's true 0.53°, which is a ~6 px dot; `SUN_DISK_ANGULAR_SIZE` widens it to ~1.4°. The glare around it is `Bloom` on the camera — bloom moved to the `bevy_post_process` feature in Bevy 0.19, which the workspace enables for exactly this. On a `SkyMode::Dome` run there is no sky pass, so no `SunDisk` either: `sky_dome.wgsl` draws its own at the same `SUN_DISK_ANGULAR_SIZE`, which is shared for that reason.
- **The whole space tier crossfades on `globe::GlobeState::space_factor`** (0 at `GLOBE_SHOW_ALT`, 1 by `SPACE_FULL_ALT` ≈ 3,000 km), never on the `in_space` boolean. Exposure, bloom, sun colour/illuminance, ambient (`apply_day_night_cycle`), the atmosphere shell height + density, and the globe surface albedo all ride it. Switching any of them at the threshold put a hard cut in the middle of a zoom — brightness, haze and glare all stepping at once. The `dev.is_changed()` gate carries a `was_space: Local<f32>` so a climb through the ramp re-applies even when the clock hasn't moved.
- **The space tier's atmosphere is deliberately taller than Earth's, and its density rides altitude.** 100 km of air on a 6,371 km ball is 1.5% of the radius — a four-pixel limb that reads as a drawn outline, not air. `globe::SPACE_ATMOSPHERE_THICKNESS` (2.5×) raises the planet `Atmosphere`'s `outer_radius` with `space_factor`; `Falloff::Exponential`'s scale is a *fraction* of the shell thickness, so the profile stretches with it. Density (`update_globe_visibility` rewrites the shared `globe::AtmosphereMedia` medium via `with_density_multiplier`) is **not** a constant column — it's thin low down (`ATMOSPHERE_DENSITY_NEAR`) so the aerial-perspective wash lifts off the detailed map, rising with altitude to the column that makes the limb glow. Below `CITY_ATMOSPHERE_ALT` it's pinned at full Earth density (this same `Atmosphere` is the city's sky dome / dawn-dusk colour). The three bands blend continuously — the old constant-column rule buried the low-orbit map under blue. Field writes on the existing component are safe; add/remove hangs the device. Bloom also rises in space (`free_camera::SPACE_BLOOM_INTENSITY`) — glare is most of what makes a thin bright limb read as air.
- **The globe's imagery is a map, not a satellite photo** — pale beige land on near-white paper, albedo ~0.8 against the real Earth's ~0.3. The sunlit hemisphere blows out from orbit. Fix it with a **tint on the imagery**, not the camera exposure: the near-white map sits on the tonemapper's shoulder, where stopping down barely darkens the surface but *does* dim the limb and stars (the faint things a space view is made of). The tint is *ramped* with `space_factor` — `globe::GlobeSurfaceAlbedo` goes 1.0 at the threshold → `GLOBE_DEEP_ALBEDO` (0.55) in deep space, applied to each globe material's `base_color` (`update_globe_albedo`, throttled; new tiles read the current value at spawn so they don't pop bright). A *fixed* tint can't do this: the globe replaces the full-brightness flat tiles exactly at the boundary, so a constant 0.55 stepped the map a stop darker the instant the globe appeared — and exposure can't compensate, being global (it would over-expose the flat tiles just below). Ramped-to-1.0-at-the-boundary is the only seam-free option.
- **Space-tier lighting is its own model** (`apply_day_night_cycle`, gated on `globe::GlobeState::in_space`): white unattenuated sun at the solar constant, Earthshine-scale ambient, fixed exposure (`SPACE_EXPOSURE_STOPS`). Running the ground curves from orbit dimmed the planet by the *anchor's* local horizon — an 18:00 fly-out showed a dim red globe instead of a sunlit day side and a dark night side. The system's `dev.is_changed()` gate carries a `was_space` `Local` so crossing the tier boundary alone re-applies it.
- **The tile workers and Bevy's screenshot readback are the same thread pool.** `platform::workers::submit` *is* `AsyncComputeTaskPool` on native, and our jobs are blocking closures (~120 ms per MVT rasterise) that own a pool thread with no yield point; `bevy_render::collect_screenshots` detaches the capture's readback future onto that same pool. A teleport queues hundreds of jobs, the pool is 3 threads wide on an 8-core host, and the streamers keep refilling it — so the readback is FIFO'd behind them and may never be polled. Nothing logs, because nothing is broken. It surfaces two ways: `--shot` renders healthy frames for a minute and writes no PNG, or (worse) it writes a **black scene with only the chrome** and exits 0, because at ground level the map is vector `surfaces` geometry still sitting on the worker queue. `workers::set_paused` is the fix — the harness quiesces the pool between the settle verdict and the shutter (`shot_harness::QUIESCE_MAX_S`) and waits for `workers::outstanding()` to hit zero. Pausing **parks** jobs rather than dropping them: the streamers de-duplicate on "a fetch is in flight", so a discarded decode never gets re-queued and the tile is missing for every later shot in a `--shots` run. Anything else spawned onto `AsyncComputeTaskPool` inherits the same starvation. `docs/notes/headless-shots-software-renderer.md` has the A/B (reproducible on a GPU by squeezing the pool to one thread — it needs no software renderer), plus the related trap that `--wait`/`--settle` count *virtual* seconds clamped at 0.25 s/frame, so on a slow renderer they run ~6× longer than they read.
- **A command outlives the entity it names, and a release build must not die of it** (`docs/notes/entity-commands-outlive-entities.md`). `commands.entity(e).insert(..)` records `e` now and applies at the next sync point; another system can despawn `e` in between, and Bevy's fallback handler answers that with a **panic**, i.e. `SIGABRT` on a phone. That is what "the viewer crashes when minimized" is: a suspended app drains no network mailbox, the socket is aborted, and the first frame back runs `session::teardown` — which despawns every server-owned entity — in the same flush as whichever streamer was queueing a component onto one of them from a query that could not see the pending despawn. **Which command it was is not established**: the crash report said `command <Enable the debug feature to see the name>`, so the Android build now turns bevy's `debug` feature on to make the next one say. Two rules follow. Anything aimed at an entity another system may retire uses `try_insert` / `try_remove` / `try_despawn` — "it is gone" is the outcome the caller wanted anyway — and the standing case is the server-owned entities, because `teardown` is unordered against every streamer while `network::apply_network_snapshot` retires the same ones from the other side. And **release builds set `App::set_error_handler(warn)`**, the same policy `handle_render_error` follows: debug keeps the panic, where a new race is meant to be found, and only the shipped artifact is forgiving. A steady stream of `Entity despawned` warnings is still a bug to go and fix; the handler is a floor, not a licence.
- **A halted renderer is indistinguishable from a hang, so the error policy is by kind** (`lib.rs::handle_render_error`, `docs/notes/android-build.md`). Bevy's default answer to a `RenderError` is `AppExit::error()`, which made the first phone run *vanish* with no Rust panic; the fix was `RenderErrorPolicy::StopRendering`, and that is **terminal** — bevy leaves the render state `Errored` for the rest of the process, so nothing is ever drawn again while the window, the input and every system keep running. On a phone that reads as "it froze, I had to restart it", with the explanation only in `logcat`. **Every kind halts, `DeviceLost` included.** Recovery was tried twice on the device and aborted the process both times (a surface still connected to the `ANativeWindow`, then a swapchain semaphore still held by the frame the handler is standing in), and deferring the rebuild to a frame boundary is upstream's job. `Ignore` on a handheld screen is a strobe. **After a device loss the acquired swapchain image can never be released by anyone** (`docs/notes/device-loss-strands-the-swapchain.md`): `wgpu-core`'s `Surface::discard` is gated on `check_is_valid()`, a lost device never is, so the raw texture stays in `present.acquired_texture` and *whatever* destroys the swapchain later — an Android suspend, a shutdown — walks into `Arc::into_inner(…).expect("…still in use by a SurfaceTexture")`. The gate is still on wgpu trunk past 30.0.0 and bevy 0.19 pins wgpu 29, so there is nothing to upgrade to. A third attempt (`release_halted_frame`) cleared every holder *bevy* has and shipped, and the device aborted anyway — the holder was never ours. What works is not releasing but **abandoning**: `abandon_lost_surface` leaks `WindowSurfaces` so nothing ever tears down that swapchain. **And on Android the process then leaves** (`exit_on_halt`, status 0): the halt is terminal, a frozen screen has to be force-closed, and a lost device also aborts in `Buffer::get_mapped_range` on pool threads no handler can reach — so staying up is only waiting to see which abort lands. Desktop keeps the frozen window; the log is already on a terminal there. **A halt writes the report the next launch shares** — a frozen picture nobody can explain is the failure mode the whole crash-reporter apparatus exists to remove — and logs once, not once per frame, since bevy calls the handler on every extract while `Errored`.
- **Destroying a GPU resource inside the render graph is not the same as dropping one, and egui's texture frees are the case that bites** (`egui_manager::egui_pass`, `docs/notes/egui-texture-lifetime.md`). `egui_wgpu::Renderer::free_texture` calls `wgpu::Texture::destroy`, which takes effect at once — including for command buffers already *recorded* and not yet *submitted*. egui retires a texture in the `end_pass` of the frame its last `TextureHandle` was dropped in, and the shapes of that same pass routinely still draw it (a window that shows an image and closes itself does exactly that). Freeing there earns `Validation Error … Texture with 'egui_texid_Managed(N)' label has been destroyed` at `Queue::submit`, which `handle_render_error` halts on — i.e. the app freezes for good, which is how a saved place's photo viewer froze the phone build. Frees are therefore **queued** at the bottom of the pass and drained at the top of the next one, after bevy has submitted. Anything else that explicitly destroys a texture or buffer owes the same one-frame delay.
- **A device GPS fix past `driver::GPS_TELEPORT_M` is a teleport, not a position write.** `driver::place_avatar` writes flat-frame metres measured from the *map anchor* and nothing in that path moves the anchor, so the everyday case — plan a route where you were browsing, tap Drive, the phone reports where you actually are — dropped the avatar and the chase camera hundreds of kilometres from the origin of a frame the tiles, buildings, terrain and route line were all still built around, and every streamer rebuilt at once (see the churn entry below). Past 2 km the fix goes through `Teleport`, which re-anchors the map, retires the old tiles through the bounded despawn queue and brings the camera; under it, the cheap write. The general rule: a *move* is a write, a *jump* is a teleport.
- **Mass mesh/texture churn hangs the Intel iGPU (`VK_ERROR_DEVICE_LOST`):** bursts of large uploads + despawns packed into few frames overrun the command-buffer timeout — the device dies, then every render system panics in `Buffer::get_mapped_range` ("Buffer with '' label is invalid" — that panic is downstream noise, not the cause). Three guards exist: the flat-tile build cap, `globe::MAX_GLOBE_TILE_BUILDS_PER_FRAME`, and the OSM detail-patch altitude freeze + refetch cooldown (`osm_buildings::DETAIL_FREEZE_ALT` / `DETAIL_REFETCH_COOLDOWN` — a zoom-out once fired 13 full patch rebuilds, 6,776→46 buildings, in 2.4 s and lost the device at 4.8 km altitude, far below the space tier). Keep any new streaming path per-frame-bounded and drift/altitude-gated. **And bound it in bytes, not only in items** (`docs/notes/upload-bursts.md`): every one of those caps counts *items*, the items differ in size by three orders of magnitude, and `lod22`'s cap — the strictest in the codebase at one cell per frame — was the path that handed the GPU **63 MB in a single frame** over Groningen (measured 2026-08-18, `systems::upload_meter`, which reports it in the `slow frame` line and as `upload_peak_asset_kb` in `--dump-state`). Two bounds now, and they are not redundant: `lod22::MAX_CELL_MESH_BYTES` cuts a cell into byte-bounded meshes, because bevy's upload budget always writes one *whole* asset per frame and so cannot spread a single huge one; `quality::Budget::upload_bytes_per_frame` (phone tier, `CARTO_UPLOAD_KB` to override) then bounds the frame across every asset path at once. A scripted capture disables the budget — deferred uploads are invisible to a settle test that watches streamers, and the first throttled shot photographed a city with no buildings and reported `settled=true`. **A rate is not a total, and the total is the other way this device dies**: the ceiling was in force on 2026-08-19 and an Adreno 840 lost its device anyway, holding ~1 GB of streamed content — deferring an upload changes when a tile arrives, never whether it stays. `UploadMeter::resident_bytes` measures it (`resident_mb` in the census and `slow frame` lines, `gpu_resident_kb` in `--dump-state`), and `quality::handset_guarded` bounds it: on Android **every** rung — including one picked by hand in Settings ▸ Graphics, which used to bypass `android_budget()` and delete the ceiling outright — is capped to a 256 px tile raster and `radius_bias` 1, which took Groningen from 991 MB to 371 MB with shadows, bloom, detail layers and native render scale all kept. Guards that belong to the *machine* go in `handset_guarded`; judgements about the picture stay in the rung. The resolved rung is logged from `Startup` (`quality::report_budget`) because `quality::init` answers before `LogPlugin` exists and had never once appeared in an Android log.
- **`MainPassResolutionOverride` does not upscale, and the phone tier's render scale is a *target* size, not a pass size** (`systems::render_scale`). The component scissors every 3D pass into the top-left corner of a main texture that is still allocated full size; Bevy's `upscaling` node then blits that whole texture — unrendered margin included — over the output with a fixed 0..1 fullscreen triangle, so the world lands in the corner of the screen with the chrome floating over clear colour. Upstream's only consumer of the override is DLSS, which owns a node that reads the reduced region; without an upscaler it is a scissor and nothing more. So the phone tier shrinks `ExtractedCamera::physical_target_size` / `physical_viewport_size` / `ExtractedView::viewport` in the render world instead (in `PrepareAssets`, before `prepare_view_targets` allocates from them, and every frame because `extract_cameras` re-inserts both components). Scale all three or none: `view.viewport` is what `view_transformations.wgsl` and the light-cluster factors divide the fragment coordinate by. The main-world `Camera` is deliberately untouched, which is what keeps `world_to_viewport`, egui layout and the touch mapping right.
- **Two directional lights must have matching shadow cascades:** Bevy 0.19's `bevy_light` panics (`index out of bounds` in cascade-visibility) if the sun and moon `DirectionalLight`s have **different `num_cascades`**, or if `shadow_maps_enabled` is toggled at runtime. Keep both at `num_cascades: 4` and never toggle shadows after spawn (see `setup_sky` / `apply_day_night_cycle`).
- **`reflect_auto_register` bevy feature is required:** glTF scenes load as `WorldAsset`s spawned by `bevy_world_serialization`, which reflect-spawns every component; without it, spawning an avatar character panics on the first unregistered type.
- **glTF animations require the `gltf_animation` bevy feature (fixed):** the earlier "animations don't play, mesh spawns in rest pose" symptom was **not** an asset-label change — it was that the workspace enabled `bevy_animation` (the crate) but not `gltf_animation`, so `bevy_gltf` compiled with its own `bevy_animation` feature **off** and `#[cfg]`-stripped all clip parsing. `GltfAssetLabel::Animation(n)` then loaded **zero** `AnimationClip`s for every glTF (fox and avatars alike). Adding `"gltf_animation"` to the `bevy` features (workspace `Cargo.toml`) fixes it. Verify with `cargo tree -e features … | grep bevy_gltf` → must show `FEATURES=[bevy_animation]`.
- **Avatars are Quaternius "Ultimate Modular" characters (CC0), mixed per slot.** Each style is a self-contained glTF (embedded base64 buffers + solid-colour materials — no external textures) with the **same 24-clip set** embedded, and 4 slot-named meshes: `*_Head` (face/hair/headwear), `*_Body` (→ Top), `*_Legs`, `*_Feet`, plus optional accessory (Backpack) and sometimes a **weapon** (Pistol/Sword). `CHARACTER_STYLES` is the catalog (`models/avatar/characters/{Man,Woman}_<file>.gltf`); clip indices are constant (**Idle=4, Run=16**; no fly clip → Idle stands in). `AvatarAppearance` is per-slot (`{sex, head, top, legs, feet, accessory}`); `resolve_avatar_holders` groups the chosen slots by character file into holders, each with a `SlotMask`. `play_avatar_animation_when_ready` hides the meshes not in a holder's mask (and always hides weapons via `is_weapon_node` — no business avatar with a gun), then plays the embedded clips (Case 1). A preset = all four slots one style → a single holder. Mixed slots = several holders (separate skeletons/players) **phase-locked by `sync_avatar_animations`** (copies the first holder's `seek_time` to the rest) so a head from one style and a body from another don't drift. `bind_external_animations` (Case 2) is the fallback for a scene with no embedded clips — currently unexercised.
- **Avatar standing height comes from THREE places, all fox-tuned to 0.45 originally** — fixed to feet-on-ground (`GROUND_HEIGHT` = 0.05): `cartopolis_simulator::state` spawn y (online), `avatar::handle_avatar_movement` gravity clamp (offline), and `geo_nav::AVATAR_GROUND_Y` (teleport / location restore). The teleport one was the sneaky one — it re-plants the avatar on every geo-nav and at startup. The models are origin-at-feet, so 0.45 (= ground + half fox height) floated them. Each present scene spawns as its own child "holder" entity so a per-scene `WorldInstanceReady` observer binds only its own skeleton; all holders play the same `AnimationGraph`, so body and clothing move in lockstep. The head/skull is welded into the base body's full-body mesh (only a thin `Face` surface is separate), so you can't graft a head-only onto an outfit — it's whole-base-body or nothing.
- **The platform seams are `native` vs `wasm`, and Android is a third thing that answers "native" to every one of them** (`crates/cartopolis_android`, `docs/notes/android-build.md`). Every `cfg(not(target_arch = "wasm32"))` in this tree was written meaning *desktop* and now also catches `aarch64-linux-android`, so a port finds them one build failure at a time. Four are fixed and are the pattern for the rest: `arboard` has no Android backend (it is now gated `not(wasm32)` **and** `not(android)`, not merely "native"); `utils::cache`'s root must come from `ANDROID_APP.internal_data_path()`, because a NativeActivity process starts in `/` and every `platform::storage` write is best-effort, so an unwritable root means the app silently re-fetches every tile forever; **stderr goes nowhere on Android**, so the one platform where the first run is pure diagnosis is the one where this tree's `tracing_subscriber` would swallow every line — Bevy's `LogPlugin` (its `android_log-sys` layer) stays enabled there instead, as it does on wasm; and `Cli::parse()` must not run, because the zygote's `argv` belongs to `app_process` and clap answers an unknown flag with `exit(2)`, i.e. the app dying on launch. A related trap has no cfg at all: `data_layers::open_url` was a per-OS chain with no fallback arm, so a target that is none of linux/macos/windows/wasm failed to compile *the whole crate* on a line about opening a browser. Prefer a catch-all arm to an exhaustive-by-coincidence one. The APK runs on NativeActivity, which needs no Java *to start* — and costs the soft keyboard, so every egui text field is unusable on the phone. It does carry a `classes.dex` since 2026-08-23: `build-apk.sh` runs `javac` + `d8` over `crates/cartopolis_android/java/`, still with **no Gradle**, because Gradle resolves dependencies and a class extending a framework type has none. Two things follow. `android:hasCode` must stay `true` — a dex under `hasCode="false"` is silently never loaded, and `platform::android::report_dex` logs at startup whether it was. And **`FindClass` cannot see our classes from `android_main`'s thread**: JNI resolves against the calling frame's classloader, a natively-attached thread has none, so it falls back to the system loader; go through `Context.getClassLoader()` + `loadClass` instead. The keyboard is *not* fixed by any of this — that is GameActivity and an AAR, which genuinely is what Gradle is for.
- **A link to a place is one URL with two destinations, and the query is the part Android cannot see** (`systems::place_link`, `docs/notes/place-links.md`). `https://cartopolis.org/go?place=53.21940,6.56650,120m,-12.5,45.0` opens the app on a phone that has the published APK and the web client everywhere else; `cartopolis://go?place=…` is the same place through the custom scheme. Three things about it are load-bearing. An **intent filter matches scheme, host and path and never the query**, so `?place=` cannot be what marks a link as the app's — hence the `/go` path (Caddy rewrites it to `index.html`; the manifest and the Caddy matcher list the same two paths and must stay in step), and hence *not* the site root, which would have claimed `/apk/` too. **App Link verification is keyed to the signing certificate**: `crates/cartopolis/assetlinks.json` carries the deploy host's fingerprint, so rotating the release key means editing that file, a locally built APK gets no App Link at all (only the custom scheme), and verification happens at *install* time so publishing the JSON afterwards fixes nothing already installed. And **the launch intent is frozen for the life of the process** — `android-activity` 0.6 surfaces no intent, `NativeActivity` never calls `setIntent`, and the trampoline activity that would fix it is a Java class this dex-less APK cannot have — so `platform::android::launch_url` is read **once**, at startup, and a link followed while the app is running brings it forward without moving the camera.
- **A touch pointer produces no mouse events at all, so touch needs its own bridge everywhere** (`systems/player/touch.rs`, `docs/notes/touch-input.md`). winit's web backend routes a `pointerType == "touch"` pointer to `WindowEvent::Touch` and emits **no** `CursorMoved` and **no** `MouseInput` for it; Bevy passes that through as `TouchInput` and `Touches`. A client reading only `ButtonInput<MouseButton>` + `CursorMoved` is therefore not *degraded* on a phone, it is completely inert — no camera, no buttons, no panels — with nothing in the log to say why. Three bridges, because three consumers need different shapes of the same events: **egui** (`egui_manager::pointer_events`) needs them in *stream order*, since a press must carry the position it had at its own point in the batch; the **world click** consumers get a mouse emulated from the primary finger (left button + `Window` cursor position), which is what makes picking, the gizmo drag, the route pick and the globe's zoom-toward-cursor work with no edit at any of those sites; and the **camera gestures** (pinch/twist/two-finger drag) have no mouse equivalent to emulate, so they are recognised into `TouchGestures` and read per camera mode. Four things are load-bearing. `Touch::delta()` is **stale on a quiet frame** — `previous_position` is only refreshed on frames carrying touch events, so a motionless finger keeps reporting its last delta and the map slides on under it; `touch.rs` tracks its own positions. Press and release are **never emitted in the same frame**, because `egui_wants_pointer_input()` is only meaningful while a pointer button is down (see the entry below) and a tap that starts and finishes inside one slow web frame would otherwise be swallowed. `touch-action: none` on the canvas is **not** redundant with winit's `preventDefault` — the compositor consults it *before* dispatching, so without it the browser eats the drag, the pinch and the double tap and no `TouchInput` ever reaches Rust. And `camera_controls` had to grow a `CameraInput` `SystemParam` to add it: Bevy caps a system at 16 parameters and it was already at the limit.
- **`egui_wants_pointer_input()` only answers correctly while a pointer button is down.** `is_pointer_over_egui()` resolves the Background layer — which egui registers over the *whole screen*, so panels and background UI can catch clicks — against `root_ui_available_rect`, and **only `Context::run` sets that field**. This client drives egui with `begin_pass`/`end_pass` and a hand-built root `Ui`, so it is never set and `is_pointer_over_egui()` is unconditionally `true`; the predicate collapses to `is_using_pointer() || !any_pointer_down()`. Every call site happens to consult it on a press or mid-drag, where that equals "egui grabbed this press" — correct by luck of the calling convention, not by being right. Consult it on a frame with nothing held and it answers `true` over the bare map. Setting the field from `end_egui_frame` is a one-line fix and is worth doing *on its own*, with the click behaviour of all six call sites re-checked — it is not something to bundle into an unrelated change.
- **`ui_owns_keyboard` must gate on `ctx.text_edit_focused()`, not `egui_wants_keyboard_input()`.** The latter is `memory.focused().is_some()` — true whenever *any* widget (a button, a selectable in the avatar chooser) holds focus, which silently swallowed avatar WASD **and** the Space/Shift fly keys until you clicked empty space. Only real text entry (search bar, rename) should yield the keyboard.
- **Avatar standing height is y=0 (feet on the ground).** The Quaternius models are authored origin-at-feet, so `simulator` spawns the avatar at `start` (not the old `+1.0`, which floated the humanoids a metre up — that offset only ever suited the fox, whose origin is its centre). The follow camera looks at `avatar_pos + 1.5·Y` (≈ chest of a 1.8 m avatar).
- **Avatar↔building collision is client-side prediction, not server physics** (`systems/player/collision.rs`). The sim (`simulator`) is authoritative for avatar position but has **no building geometry** — OSM/3DBAG footprints stream only on the client. So both building streamers publish 2D footprint polygons into the `BuildingColliders` resource in the anchored world-XZ frame (`osm_buildings` = exact detail-patch rings; `lod22` = a convex hull of each 3DBAG building's projected vertices, since only a triangle soup survives there — cleared/rebuilt per cell and on re-anchor). Collision then acts on whichever channel owns movement in the current run mode: **online (server-authoritative)** steers the *velocity wish* in `network::send_network_intent` (`steer_velocity` slides along walls and auto-walks a trapped avatar out — a snap-eject can't work there, the next snapshot would overwrite the transform); **`--offline`** moves the transform directly in `avatar::handle_avatar_movement` (`slide`) with `collision::eject_avatar_from_buildings` as a snap-out backstop. Gated on `DataLayers::buildings_enabled` (collision matches what's drawn) and skipped whenever the avatar is off the ground (`avatar::AIRBORNE_EPS`) — the footprints carry no height, so applying them to a flight or a fall diverts the avatar around a building it is passing far above. `avatar_state.position.xz` is the avatar's absolute world-XZ (the avatar sits near origin and the world re-anchors around it), so it compares directly against the footprints.
- **`bind_external_animations` (avatar Case 2) is the fallback for a scene with no embedded clips** — it roots an `AnimationPlayer` on the `Armature` node and hashes each bone's name-path into the `AnimationTargetId` `bevy_gltf` would have assigned, so clips from a *separate* glTF (matching skeleton) bind and play. Currently unexercised (the Ultimate Modular characters all embed their own clips → Case 1), but kept for future modular content on a shared rig.
- **The avatar's speed model lives in `cartopolis_core::motion` + `systems::locomotion`, and the wire carries a throttle, not a speed.** `SimWorld::apply_intent` derives speed from the *magnitude* of the wish vector, so stroll (Alt, 1.1 m/s) / walk (default, 1.8) / run (Shift, 6.0) / flight are four magnitudes the client picks — no protocol field, and prediction cannot drift from authority because both call `motion::sim_speed_for_wish`. Speed **ramps** in m/s² rather than being assigned (a normalized ease reaches every gait in the same time, so a run start feels as light as a stroll start), and the travel direction is *held across a key release* or the avatar stops dead the frame the key comes up. `handle_avatar_movement` owns this in every run mode and `send_network_intent` consumes it — two systems deriving the same velocity from the same keys is how the offline and online paths came to behave differently. **The clip is chosen by ground speed and played at `ground_speed / clip_reference_speed`**: `Run` used to play at a fixed 1.0× while the avatar moved at 8 m/s, so the feet ran at half the speed of the ground — the ice-skate that read as "sluggish". `Walk` (clip 22) is loaded now and gait changes cross-fade through `AnimationTransitions` instead of `stop`/`play`. **The unmodified gait is a walk, and that is a constraint, not a taste**: the default used to be a 4.2 m/s jog, i.e. above `GAIT_CLIP_SWITCH`, so pressing W ran, the walk clip was reachable only by holding Alt (which several compositors swallow), and a start from rest paid *two* 180 ms cross-fades inside a quarter second. `locomotion`'s suite pins the relation. A gait change also **carries the stride phase** across (`avatar::apply_pose`): both locomotion clips are two footfalls long, so the incoming one is seeked to the outgoing one's normalized phase — `AnimationTransitions::play` otherwise starts it at feet-together and the fade interpolates the legs through a pose they never occupy. `docs/notes/avatar-game-feel.md` has the measurements.
- **Sitting on a bench is a clip this client writes and an offset it carries** (`systems/player/sit_pose.rs`, `docs/notes/sitting-down.md`). The Quaternius set has no sit — as it has no jump and no flight — but a lean could not stand in for this one, so `sit_pose` builds an `AnimationClip` at spawn out of eleven constant curves and pushes it into the same `AnimationGraph` as the loaded ones; it then cross-fades and phase-locks like any other. The pose is **solved from the rig, not tabulated**: hips at seat height, ankles a thigh-length in front, knee from the two-link solution — which is what makes one piece of code fit both the men's and the women's skeletons (the women's legs are ~5 cm longer). Three rig facts are load-bearing: the pelvis carries a **27° yaw in every clip** which the `Torso` above it cancels (setting it to identity turns the shoulders off-axis, and its consequence is that each foot must be placed relative to *its own* staggered hip); the **feet hang off `Root`, not off the shins**, so bending a knee does not carry the foot; and only the legs and pelvis are keyed, everything above holding the idle's upper body. The other half is that the avatar cannot *stand* where it sits — the bench is a solid prop and, online, the sim owns the position and has never heard of a bench — so `resources::Seated` is a **display offset** applied to the model holders beside the flight lean, exactly as `terrain_lift` is applied to the display position. Ask `is_seated()`, never `seated.is_some()`: a seat outlives the decision to get up so the slide can unwind. **It is on the wire (protocol 19) as an offset, not a place** — each client anchors its map somewhere else, so a delta survives the difference between their frames and a position does not, and the facing is already the replicated `yaw`. It is a *level*, resent while the sit lasts, so an avatar arriving mid-sit is drawn sitting; the blend is **not** replicated, each viewer eases onto the offset itself. The sim cannot check that a bench is there, so it does the two things that need no map: bounds the offset (`MAX_SEAT_OFFSET_M`) and drops the seat the moment the same intent asks to move, fly or jump — otherwise sitting is a way to walk around displaced from your own position. `--ui sit` is how a headless capture photographs it.
- **`cartopolis_core::motion` is shared with the sim on purpose — do not re-inline it.** The fall/climb/speed rates were three private copies (sim, prediction, offline) each with a comment asking the next person to keep them in step. A mismatch between the first two is invisible except as rubber-banding; between the first and third it means the same key produces a different world depending on how you launched. Gravity is a real acceleration now (22 m/s², above Earth's so a jump doesn't hang like the moon) rather than the old constant 12 m/s descent, which had no acceleration in it at all.
- **Jump needs the sim; emotes need the wire (protocol 13).** `SimWorld::step` clamps `y >= 0` and falls anything not flying, so a purely predicted jump is reconciled straight into the floor — hence `ClientIntent::jump`, granted **only from the ground** so holding the bit cannot climb. Both jump and emote are *edges*: they bypass the send-on-change test, the keepalive throttle and the server's `MIN_INTENT_INTERVAL`, because a skipped movement frame is corrected by the next intent while a skipped jump simply did not happen. A live emote is held on the wire for `EMOTE_REPLICATE_SECS` so a client arriving mid-wave still sees it, which means receivers must diff on `EmoteState::sequence` — diffing on the emote itself restarts the clip 20 times a second.
- **Keys moved:** `E` is **interact** (it was the flight climb key; climb is `R`), `Space` is **jump** on the press and **take off** if held past 0.25 s — a jump that waits to see whether a hold is coming is not a jump — `F` is still the unambiguous flight toggle, `Shift` runs, `Alt` strolls, and `1`–`6` are emotes.
- **The follow camera's boom collides in 2D and only below 15 m.** Building footprints carry no height at all, so above a plausible eaves line a 2D hit means "there is a building over there", not "the view is blocked" — acting on it reels the camera in every time the avatar walks past a block. `CAMERA_COLLIDE_MAX_Y` is the gate to delete if heights ever reach the collider index. The boom comes in fast and goes back out slowly, or every doorway makes the camera lunge.
- **The trees, the street lighting and the garden boundaries are surveyed now, not invented** (`systems::surveyed`, cartopy's `server/pipeline/bgt.ts`, `docs/notes/surveyed-street-objects.md`). `scatter.rs` and `furniture.rs` each said in their own module note that they were guessing: Shortbread carries canopy *areas* so the trees were scattered, and its `pois` layer has no street lighting at all, so the map had no lamppost anywhere. The BGT registers all of it object by object. Four things are load-bearing. They are **added** to the generated layers, never substituted: the BGT's tree points are *optional* content and coverage varies by municipality — Groningen's own centre has none, every record there retired in 2023 — so replacing the scatter where surveyed data exists would delete a park's canopy in exactly the densest cells. The API returns **every historical version** alongside the current one, each carrying an ordinary `status: bestaand`, so `termination_date` is the discriminator and skipping it grows a ghost set of trees where trees used to be (`datetime` looks like the right filter and returns nothing). Boundaries are meshed as **one box per surveyed segment** rather than by walking the line in fixed steps — the segments average 6.4 m, so a fixed step triples the count *and* cannot land on a corner, which gaps every bend on the outside and overlaps it on the inside. And **solid and interactable stopped being the same list** (`world_places::prop_interactable`): every furniture instance used to become both a collider and a proximity prompt, which was fine for a layer of things people visit and is not fine for a city's worth of lampposts.
- **Buildings have doors you can walk through, and one room behind them** (`systems::interiors`, `docs/notes/doors-and-rooms.md`). The register already knew where every door was: the BAG registers each addressable unit with a point at or near its entrance, which is the closest thing to a national door-position dataset there is. It now rides on the *building's* record in the small file `lod22` fetches, not in the 2 MB places file only the readout reads. The BAG's **outline** ships with it, which also retires an old approximation — a 3DBAG building is a triangle soup whose only recoverable footprint is its **convex hull**, and a hull fills in the inner corner of every L-shaped building with a collider nobody can walk through. **Two bugs of one shape are the lesson here.** The door's outward normal was derived from the ring's signed area, which is the tidy answer and is the wrong way round in a frame where +z runs south: every door in the city was drawn inside its own wall, the count read **113,710**, and the street showed none — a capture cannot tell "there are none" from "I am not looking at one", and an hour went on camera angles. The room walls had the identical assumption and would have failed identically silently. Both **probe** now — step 5 cm off the surface and test whether that lands inside the ring — which is true on any winding and any shape, and both are pinned by a test that runs the ring both ways round. The room is a **near-camera layer** (70 m, rebuilt every 15 m of walking, ~1,500 triangles standing) and **one storey**: the register says how many units a building holds and never where its floors are, so a full-height empty volume would be a sixteen-metre shaft with a front door. Its walls are inset from the outline so they cannot z-fight the shell, and the doorway is cut out of the room's wall at **the same points the collider opens at** — a room whose wall crossed its own door would seal the avatar in behind a surface they had just walked through.
- **The pavements are surveyed and the carriageways are still OSM's, on purpose** (`cartopolis_geo::paving`, `docs/notes/surveyed-street-objects.md`). The obvious use of the BGT's road surfaces replaces `tessellate_roads` with its polygons, and that loses more than it gains: an OSM ribbon carries a road *texture* (lane dashes, edge lines, ballast), a kerb casing and a rung on the per-vertex depth ladder, and **the BGT has no markings at all** — its own `weginrichtingselement_*` collections are `niet-bgt` on every feature. So the split is by what each source is good at: OSM keeps the vehicle network everywhere in the world, and the BGT supplies what lies beside it — pavements, cycle paths, parking bays, driveways, verges, islands — which OSM draws as a thin constant-width line or not at all. The single overlap is `RoadClass::Path`, and those ribbons are suppressed over a covered cell (`tessellate_roads`' `surveyed_paths`) so no ground is drawn twice. Paving takes its own depth rung **between the ground fills and the road band**, which is what makes the mixture safe: the two sources disagree by centimetres about where a kerb is, and with the road above, the overlap reads as tarmac meeting the kerb instead of as a z-fight down every street. Two numbers to know: simplification is mandatory (a page of `ondersteunendwegdeel` is 77,202 vertices of which **4,792 survive a 10 cm Douglas-Peucker** — 94% is collinear filler, and without it a city is hundreds of megabytes), and even simplified this is the **second-heaviest thing the client streams** at 3.8 MB for the densest cell.
- **One prim reaches another only over a channel, and that is what makes a button possible** (`vfSend` / `vfListen` / `on_message`, `docs/notes/prim-scripting.md`). Every `vf` call acts on the script's own prim — `prim_id` is captured by the host and is not an argument, which is the authorisation surface working as designed and also meant a button could not reach the thing it controlled. Four properties, each chosen against an alternative: a message **never leaves the script host thread** (it is not a `ScriptCommand`; routing a button press out to the tick loop and back would put it behind the world's write lock for nothing); delivery is **after the whole round-robin pass**, so it lands next tick and a script's behaviour does not depend on where the scheduler's cursor was; **listening is opt-in**, or one chatty prim costs every other script in the region an event per tick; and **a script does not hear itself**, the one deviation from Second Life here — listening on the channel you send on is the ordinary shape and hearing yourself makes it a feedback loop nobody wrote. Channels are scoped to the **region**, because one that crossed would let an estate's button work its neighbour's door.
- **The world can be authored from a shell, and that is a separate surface from the wire** (`crates/simulator/src/authoring.rs`, `tools/author.py`, `docs/notes/authoring-content-from-outside-the-viewer.md`). `/api/admin/prims` creates, patches, scripts and deletes prims with an admin token and no viewer — the in-world tools all need a person, a GPU and a session, which made building a world from a file, restoring one, diffing one, or setting one up from an agent with no screen impossible. It is HTTP for the reason account management is: an operator action must not run an authorisation decision through the same path as a movement intent. Three things to know. It goes through **`SimWorld`, not SQLite** — the world is the authority and holds prims in memory, so a row written behind its back is invisible until a restart. **Absent is not null**: a `PATCH` naming one field changes one field, while an explicit `null` clears one, and serde needs the `present` deserialiser to tell those apart. And a **200 does not mean the script compiled** — the host compiles on its own thread and answers with a `ScriptOutput` on the wire. **The content it installs belongs to the simulator, not to the tool**: `crates/simulator/src/content.rs` defines the packs and `include_str!`s their Luau from `crates/simulator/content/`, so `tools/author.py install firebird` is one POST with a name in it. It began as a `.lua` file in the tree that the Python read and posted, which is wrong twice — the definition of a demo is a statement about this world, and a deployed simulator has no repository beside it. Installing twice **replaces**, matching on `prims.origin` (schema V14) rather than on the prim names a pack declares: the beacon's own script renames it, so the name version left the old one standing and added a second. The worked example is the firebird and the beacon that calls it.
- **A prim's particles are a formula, not a simulation** (`systems::particles`, `assets/shaders/particles.wgsl`, `docs/notes/particles-are-a-function-of-time.md`). `ParticleEffect` is fourteen numbers on the prim; the shader computes every particle's position, size, colour and lifetime from those, the clock and its own index, over one shared quad pool built at startup. Nothing is stepped on the CPU and an emitter uploads nothing after it is built — the alternative, a `Vec<Particle>` rewritten into a vertex buffer each frame, is the documented device-loss churn made continuous, and it would have to replicate at the tick rate to look the same on two screens. `systems::grass` made the same trade first. What it costs is real and permanent: nothing collides and no particle can be individually addressed. Four load-bearing details — a **burst is a level with a `sequence`** (a one-shot message would be missed by a client whose snapshot lands a tick late, and diffing on the effect itself replays the same bang forever); the emitter is a **child entity whose translation alone is read**, so it inherits the prim's `GridCell` under `big_space` and *not* its rotation or scale; **frustum culling is off** because the quads are placed metres from the mesh's own vertices and the derived AABB is the wrong volume; and `AlphaMode::Add` is premultiplied, so the fragment writes **alpha 0** to reach pure additive. Colour and blending are not evidence on this container's rasteriser — `particle_emitters` / `particle_quads` in `--dump-state` and `--ui fire` are the geometry half that is.
- **A person's own build can leave the server and come back, and ownership is what scopes it** (`GET /api/content/export`, `POST /api/content/import`, schema V15's `prims.owner`, `docs/notes/authoring-content-from-outside-the-viewer.md`). Deliberately **not** under `/api/admin`: they take `require_session`, so any signed-in account may export, and the *default* scope is `owner = me`. That default is the security property — a player cannot reach past themselves by any argument they supply. **An admin may always export**, including `?owner=<username>` and `?all=true`, which is not a hole: an operator can already read `world.db` over ssh, so refusing would buy no confidentiality and cost the thing the route is for, taking a copy of the world before changing it. `?all=true` is also the only way to reach prims with no owner (everything before V15, and everything a content pack installs) — those belong to the server. `POST /api/content/transfer` hands prims to another account: the owner may give their own away, an admin may re-home anything, and it is **all-or-nothing** — every prim is checked before anything is written, because a partial transfer leaves the caller unable to tell which half happened. The document is `{version, prims: [PrimSpec]}` — the *same* type the create route accepts, so an export is a request you can post back — and it drops the id, the region and the `position.x/z` echo, none of which mean anything on another server. **Import adds rather than replaces**, the opposite of a content pack: a pack knows what it installed last time (`prims.origin`) and a document does not, so replacing would have to guess and guessing wrong deletes a build. Ownership is recorded on the wire's `CreatePrim` only and is not in `PrimDto`. It **gates editing**: `UpdatePrim`, `DeletePrim` and `SetPrimScript` are refused unless you own the prim or are an admin — and the script store is the *same* gate rather than a lesser one, because a script can move, rename, ignite and delete a prim, so scripting somebody else's object is the most complete way to take it over. An unowned prim belongs to the server and only an admin may change it, which is what stops a passer-by deleting the beacon. The admin flag is read **once at the handshake** (the same freshness `disabled` already has) and the owner map is in memory (`SimWorld::owners`), because `UpdatePrim` arrives at the gizmo's drag rate and neither check may put SQLite on the movement path. **A refusal carries the truth**: the dialog and the gizmo apply an edit locally before the server answers, so a refused client would otherwise draw something that never happened forever — `PrimUpsert` is only sent when something *changes*, and a refusal changes nothing. `net::refuse_and_correct` sends the authoritative prim after the 403 and the client deselects on that code first, because upserts for the prim being manipulated are deliberately ignored.
- **Walking up to a scripted prim offers to press it, and that needed one bit on the wire** (`systems::interact`, `PrimDto::scripted`, protocol 21). Until this the only way to touch a prim was the right-click context menu's Touch entry — an edit-flavoured developer path, which is not a button anybody finds. The prompt `interact` already draws for streamed places now also resolves prims, and a prim wins where both are in range: a place is scenery the map happens to name, a scripted prim is something somebody *put* there. It is gated on `scripted` because the client cannot derive it — script source is deliberately kept out of `WorldSnapshot` — and without the gate every crate in the city would offer to be pressed. Matching is through the **geo anchor**, not the prim's `Transform`: that transform is a `big_space` cell-local offset while the avatar's position is absolute anchored world XZ, and comparing them directly is the frame mistake this whole area is about. **A plain left-click on a scripted prim also touches it** (`picking::prim_picking`) rather than selecting it — Second Life's rule, and the one everybody expects: you click the button, you do not select the button. Shift-click still selects and the right-click menu still has Edit and Script, so a builder loses nothing. The proximity prompt was shipped first and was not enough: the beacon on the Grote Markt proved it, when the person it was built for went looking and could not work it.
- **A script moves a prim with `vfSetGeo`, and senses an avatar with `vfSensor`** (protocol 20, `docs/notes/prim-scripting.md`). `vfSetPos`'s x/z have always been a client-frame echo re-derived from the geo anchor (ADR-029), so horizontal motion was undone by the next re-anchor; `vfSetGeo(lat, lng)` writes the anchor itself and `vfGeoScale(lat)` turns metres into degrees. The sensor needed a wire change of its own and could not have been done without one: an avatar's sim position is metres in **its own client's** anchored frame, so two avatars in two cities both sit near the origin and "is anyone near this prim?" has no answer there. `ClientIntent.geo` is the avatar's client saying where on Earth it is; `SimWorld::script_views` measures it against each scripted prim's anchor once a tick and pushes the result *with the view*, because the script host holds no reference to the world. An avatar that has sent no fix is not seen, which is the honest answer rather than a guessed position.
- **An IFC building model can replace a building's shell, and that is what makes one hollow** (`systems::lod3`, `tools/ifc_lod3.py` — one of the two extractors that stayed Python, `docs/notes/importing-a-building-model.md`). Keyed on the identificatie, so "which shells do I skip?" is a set test rather than a geometry match against a building that may have been extended since. Its surfaces are drawn **double-sided** — culling is right for a shell and wrong for a building you can stand in — and collision comes from the **walls**, because hulling a model the way a shell is hulled seals it, doorway included, and a floor slab's hull is the whole storey. Two traps. `ifcopenshell.geom.settings()` returns each element in its **own** frame: without `use-world-coords` a two-storey model imports as one storey with every wall stacked on the same spot, and it looks entirely plausible — right element count, right classes, right triangle count — so only measuring the output extent catches it. And georeferencing is an **argument, not a discovery**: a model handed over by an architect routinely carries no `IfcSite` coordinates at all, or a project origin 150 km away.
- **The four Dutch extractors live in [`jeroen/cartopy`](https://code.garage44.eu/jeroen/cartopy) now, not in `tools/`** (`docs/notes/where-the-map-data-is-built.md`). `server/pipeline/{buildings,lod22,bag,bgt}.ts` over there, driven by the Data tab of the admin GUI instead of by four ssh commands per city. What that costs is the seam: **the parsers for all four formats are in this tree** — `lod22.rs`, `building_facts.rs`, `surveyed.rs`, `osm_buildings.rs` — and nothing but a person keeps the two repositories in step, so a renamed key compiles fine here and arrives as a layer that draws nothing. cartopy's `server/pipeline/format.test.ts` pins each shape against captures of a real run and is the nearest thing to a specification either side has; read it before changing a wire format, and change both. The port was diffed against the Python it replaced over a 1 km square of Groningen — `buildings`, `bag` and `bgt` are structurally identical, `lod22` differs only in which diagonals earcut picks. `tools/ifc_lod3.py` and `tools/ifc_demo_building.py` stayed, because `ifcopenshell` has no JS equivalent and importing one building is not a pipeline.
- **A drawn building carries its BAG number now, and that is the join to everything else** (`systems::building_facts`, cartopy's `server/pipeline/bag.ts`, `docs/notes/building-identity-and-bag.md`). The LoD2.2 extractor used to write "the last 15 digits" of `NL.IMBAG.Pand.0014100010903891-0` as an int and call it "stable-ish" — which it was, as an internal dedupe key and nothing else: the part suffix contributes a digit, so the truncation shifted the number, and the leading zeros that name the municipality were gone. The client discarded it anyway. It is the **identificatie verbatim, as a string**, because that is the key BAG, the address register, the monuments register and any BIM model of the building are all joined on, and matching a mass to a model by geometry is the only alternative. A second per-cell tree (`bag/{14}/{x}/{y}.json`, from PDOK's keyless BAG WFS) carries year built, use, floor areas, status, per-unit addresses with their **entrance points**, and the houseboat berths that have no building at all. Four things follow. The facade palette is chosen by **era** and the night window lighting by **use** — both ride existing channels, the era through the vertex colour and the occupancy through that colour's **alpha**, which was a constant 1.0 and is free because the material is opaque (the same spare-channel trick as `globe_ocean`'s sea mask, read at the same point, before `alpha_discard`); **1.0 means "nothing known" and reproduces the old look exactly**, which is what makes the change safe outside the Netherlands. `lod22` fetches its own cell's facts *inside its mesh job* rather than reading the `BuildingFacts` resource, because a colour baked into a vertex must be known on the worker that writes it — sharing one parse would mean a terrain-style retear on every facts cell that lands. A building the register marks `Demolished` or `NotRealised` is **not drawn** (3DBAG's solids are a dated snapshot; nothing weaker than those two qualifies). And the extractor pages that WFS at **1000** features, not 10 000: it truncates there whatever you ask for and usually omits `numberMatched`, so the ordinary "a short page means the last page" loop ends after the first thousand buildings and reports nothing — the sibling LoD1.2 extractor's 10 000 is correct for the *3DBAG* WFS and is not shareable.
- **The `pois` and `addresses` tile layers are read now (`systems::places` → `systems::world_places`)** out of the same `TileData` parse `map_geometry` already does, so they cost no request and no extra decode. They feed the proximity prompt (`systems::interact`, E to act) and the house-number readout; street furniture from the same layer also becomes circle colliders, so benches are solid. Two traps in the data: **a tile carries a buffer**, so a correctly-decoded POI can sit a few metres *outside* its own cell (clamping would be the wrong fix — the coordinate is right), and **`housenumber` is frequently a numeric MVT value**, so reading only `Value::String` silently drops most of them. Everything is keyed by cell and dropped with the cell, exactly as the street labels are.
- **Audio is the `audio` cargo feature (on by default), because `bevy_audio` pulls `alsa-sys` and that hard-fails without `libasound2-dev`.** Headless hosts that can't install it build with `--no-default-features`. That reason is Linux-desktop-only, and being a *default* made it read as a platform capability: Android and the web both passed `--no-default-features` for an unrelated reason (dropping the since-removed `solo` feature, whose SQLite they couldn't cross-compile), cargo cannot drop one default and keep another, and so both shipped **silent** for months — no footsteps, no wind, no driver turn cues, reported by nothing, since the module is `#[cfg]`-ed out entirely. Both lanes now name `audio` back (`crates/cartopolis_android/Cargo.toml`, `index.html`'s `data-cargo-features`, and the CI wasm check), and any new lane that turns the defaults off must too. Neither platform needs ALSA — cpal resolves to AAudio and to WebAudio. The browser needs one thing more: an `AudioContext` built without a user gesture starts suspended and cpal calls `resume()` exactly once, at startup, so `index.html` subclasses the constructor and resumes on the first gesture. `docs/notes/audio-off-platform.md`. Every sound is **synthesised into WAV bytes at startup** (`systems::soundscape`) rather than shipped: `.gitattributes` tracks audio by extension, so a shipped footstep would be an LFS object with the documented silent-failure mode. The synthesis and the volume/step-rate maths are pure functions so they stay compiled and tested on a host that cannot build the backend; only the ECS wiring is gated. **A synthesised clip must keep headroom, and the suite asserts it**: the wind loop was `lp2 * 6.0`, i.e. peak 1.000 with 1.08 % of its samples clamped by `to_i16`, and clipping a low-passed rush manufactures exactly the top end the filter existed to remove — so it arrived as a wind *tunnel* at any playback volume, which no `Volume::Linear` can undo because the distortion is in the asset. Footsteps had the matching fault in the other direction: one pole at 90 ms measured a ~2.5 kHz zero-crossing rate, a bright hiss fired 2–3 times a second, which reads as wind rather than as walking. Both were re-cut against measurements on 2026-08-16 (two poles, ~320 Hz, 70 ms; wind at ~120 Hz with 3 dB spare), and `AppPrefs::effects_volume` is the slider for the half only the listener can judge.
- **Proximity voice is client-complete now, and its codec is a client concern by design** (`systems::voice`, `docs/notes/voice-chat.md`). The wire (protocol 15) and `ChatHub`'s fan-out shipped long before anything could speak; what was missing was capture → encode → send and receive → decode → play, which is this module. Four things are load-bearing. The codec is **IMA ADPCM at 16 kHz** — 164 bytes per 20 ms frame, inside the sim's `MAX_VOICE_BYTES` with room to spare — and **Opus was rejected on toolchain grounds, not quality**: every Rust binding compiles libopus through `cc`, which is a C prerequisite on the Android and wasm lanes this feature exists for. Every frame **carries its own ADPCM state**, so a lost packet costs 20 ms rather than the rest of the conversation. Frames must be **paced**: `net.rs` refuses anything closer together than 15 ms and says nothing when it does, so a client that flushes a backlog in a burst loses all but the first frame and looks like a codec bug. And playback is a custom `Decodable` asset through the *existing* output device — a second `cpal` output would fail on a raw ALSA device and would need its own `AudioContext` unlock on the web. Attenuation uses the server's `distance_m`, never a Bevy spatial emitter, so it is the same in every camera mode.
- **The microphone works on Android, and it took a permission rather than a backend.** cpal 0.17's Android host is AAudio and implements *capture* as well as playback, so `platform::audio`'s cpal arm compiles and runs there unchanged — the arm is no longer `not(target_os = "android")`. What it needed is `RECORD_AUDIO`, which is `dangerous` and therefore a runtime ask: `platform::android::ensure_permission` is the generalisation of what the location provider already did, and it is called **from the capture thread** because the answer can only be polled (`onRequestPermissionsResult` is a Java override a dex-free app cannot supply) and the wait is up to two minutes. `AudioInput::available()` now answers `true` on Android; it still promises only that a backend exists, never that a device opened or that the user agreed — those arrive as `AudioInput::error`. **None of it has run on a device**: this container has no audio hardware at all, so capture, the permission dialog and audibility are all unverified (`docs/notes/container-audio.md`).
- **The avatar faces where it walks, and flight is a pose, not a clip** (`systems/player/avatar.rs`, `docs/notes/avatar-locomotion.md`). `AvatarState::facing_yaw` is the single facing — the render transform, the replicated `display_yaw` and the follow-and-rotate camera all read it — and `advance_facing` eases it toward the *wish* direction, so A/D turn the avatar a quarter turn and S brings it about. It is deliberately not the camera azimuth (that made A/D a sideways moonwalk) and deliberately not the `Run_Left`/`Run_Right`/`Run_Back` strafe clips the set does contain. **Flight is explicit on the wire** (`ClientIntent::flying`, protocol 12): the vertical keys (E up, Q down) do nothing unless flying, and `SimWorld::step` falls an avatar that isn't — the sim has no gravity otherwise, so switching flight off in mid-air used to leave the avatar hanging there forever. Fall/climb rates are duplicated in three places (`cartopolis_simulator::state`, `network`'s prediction, `avatar`'s offline path) and must stay equal or prediction fights reconciliation. The airborne *animation* doesn't exist — the Quaternius set has no flight clip and the UAL library's can't bind (different rig) — so `update_avatar_model_pose` pitches the model holders forward instead, on the holders and not the avatar entity, whose transform is the authoritative position and yaw.
- **`--shot-mode avatar` frames the avatar (the way to check avatars).** It only does so because `shot_harness::hold_scripted_camera_mode` holds the mode every frame: Follow is not offered offline (`free_camera::follow_available` wants a session) and every scripted run is offline, so before that the camera dropped to Fly one frame after the teleport and the mode silently did nothing. Free/earth shot modes put the camera at `--at` while the avatar sits at the map anchor — they usually don't coincide, so the avatar is off-screen (this caused a lot of "the avatar isn't rendering" confusion when it was fine, just elsewhere). In avatar mode `place_camera` puts the follow camera on the avatar: `--at` altitude = follow distance, `--look` = (elevation°, azimuth°). Use it at scale 1.0 instead of giant-scaling to hunt the avatar in a free-cam shot.
- **The routing graph must be noded, and skipping it fails silently** (ADR-037, `systems/geo/routing.rs`). Tiles at a zoom share one integer lattice, so a way clipped into two tiles yields the *same* global node in both — stitching needs no tolerance. What it does need is `RoadGraph::finish`: Shortbread merges ways by attribute and generalises each merged feature independently, so a side street's tee is an interior vertex of the main road's line and simplification is free to drop it. That leaves 14% of nodes (measured on the Groningen fixture) lying exactly *on* a segment while being a vertex of neither, and the largest connected car component covers only 58% of usable nodes — ordinary cross-town routes then return `NoPath` with nothing in the log. `finish` splits every segment at the nodes on it (~0.55 m) and takes that to 92%. **Snapping must target the routable core, not the nearest node** (`RoadGraph::routable_core`, the largest SCC of the mode-filtered graph): a car snapped onto a genuine one-way residential street (`oneway=yes` in the source, so the parse was right) whose forward-reachable set was a three-node dead-end pocket, and the cross-town route returned `NoPath` — while the same pair routed for bikes, which ignore one-ways. `route` snaps both ends into the largest SCC so a path is guaranteed to exist between them; a stub a few metres off the through-road is never a valid start. **Range is capped by tiles, reported as distance, and a long route drops a tier rather than being refused** (`routing::plan_corridor`, `docs/notes/long-routes.md`): street level (`ROUTING_ZOOM`) while the corridor fits `MAX_ROUTE_TILES` (~`MAX_ROUTE_KM`, 22 km), otherwise a `LONG_HAUL_ZOOM` (z10) corridor for the haul plus a detailed patch at each end, spliced by `route_staged` — out to ~`MAX_STAGED_KM` (360 km), past which `TooFar { km }`. The capsule half-width grows with `√direct`, not linearly, or a long route gets both long and wide and the tile count blows up (a cross-province query once asked for ~700 tiles). The two endpoint patches must be **separate graphs**: in one graph the routable core is whichever patch is bigger, the far end is unsnappable, and every staged route silently falls back to the coarse one. Turn instructions are likewise only emitted at real junctions (≥3 usable neighbours) with the angle measured over a 25 m window either side; per-vertex classification narrates a curving street as "bear right, bear left, bear right…". **The drawn route line is a coplanar-ground problem, not a mesh problem.** Two independent failures hid it completely and neither logged anything: the ribbon triangles were wound downward (backface-culled — `navigation::ribbon_faces_up` pins the winding now), and at `ROUTE_Y = 0.12` the line lost the depth fight with the ground stack and rendered as horizontal bands. It sits at 0.5 m with `depth_bias` ~20 (the surfaces top out at 4). `ShotMetrics` carries `route_meshes`/`route_rendered` so "not spawned" and "spawned but not rendered" are one `--dump-state` apart; when both are non-zero and nothing is visible, widen the line and colour it magenta for one capture — that separates "placed wrong" from "depth-fighting" in a single frame. **The line uses bevel joins, not mitre** (`navigation::ribbon`): a mitre offset runs to infinity at a sharp turn, and on the sub-metre segments the noded graph emits it shot a spike across a junction (a "giant arrowhead") — each segment is now a butt-ended quad plus corner-fill triangles, which cannot spike or pinch, and the material is `cull_mode: None` so winding can never hide it again. **The full-width ribbon covers only the road path**, not the raw start/end pins: the pin-to-road gap is a thin connector, so a pin that snaps across a canal to reach a drivable road draws a thin lead-in, not a fat line through water. **And the line's width rides the camera altitude, in powers-of-two bands** (`navigation::route_width_scale`): world geometry six metres wide is a comfortable fifteen pixels at 1 km and a *third of a pixel* at 30 km, so planning a cross-town drive drew a bare map with two pins on it and nothing between them — correct, present, invisible. Screen space is not available (the line lies in the road surface and takes the sun, the terrain and the depth ladder with it), so the metres are scaled instead; the band is in the mesh's redraw key, because a width that tracked altitude continuously would re-triangulate the whole route every frame of a zoom, which is the documented device-loss churn. **Solving a route frames it** (`drive_route_solver`) — there was a "Fit" button and it is gone, being one tap standing between the user and the thing they had just asked for. Not in Follow mode, where a teleport would bring the avatar with it, and not under the shot harness, where `--at` states where the picture is taken from. `frame_route`'s ceiling is *under* `GLOBE_SHOW_ALT` for a related reason: the route carries `HideInSpace`, so framing a 400 km route from 60 km up flew to a viewpoint where the line is not drawn at all. Routing needs a **vector** `CARTO_TILE_URL`; against a raster template the planner says so. `cargo test -p cartopolis solves_a_real_route -- --ignored --nocapture` prints a full turn list; `CARTO_ROUTE_FROM`/`CARTO_ROUTE_TO` ("lat,lng") override the `--ui route` demo seed to reproduce a specific route headlessly.
- **Driver mode is what strips the map — planning a route is not** (`systems/nav/driver.rs`). "Minimal mode" (`data_layers::apply_minimal_mode`) used to key off the Route *panel* being open, so looking a route up turned off the buildings, the trees and the weather, and closing the panel also erased the drawn line. Both are now tied to driver mode; the route line stays drawn until it is cleared. Four things about it are non-obvious. **The heading is a course over ground, never the avatar's facing:** `avatar::handle_avatar_movement` turns the avatar toward its camera-relative *wish* direction, so the facing is a smoothed function of the camera and the keys held this frame — it lags every turn, holds the last heading when nothing is pressed, and doesn't exist at all for a device fix. Reading it back would pin the arrow up-screen in every orientation, north-up included; the course comes from successive positions, with the fix's own Doppler course preferred when the device reports one. **Hiding the avatar needs both levels:** it is spawned with only `Avatar` + `Transform` and no `Visibility`, while each model holder under it has one, so a holder is its own propagation root and `Hidden` on the parent alone changed nothing; the holders are written too, but *only the direct children* — deeper glTF nodes carry a permanent `Hidden` from the slot mask, and restoring those to `Inherited` un-masks a mixed avatar. **The camera aims ahead of the arrow, not at it** (`CameraState::drive_lookahead`, read by `free_camera`'s Follow arm): a chase cam that looks at the vehicle centres it and spends half the screen on road already driven. And **every anchored box pins its own width** — the first bottom bar used `vertical_centered` inside a size-to-content `Area`, hit the same feedback loop `hud`'s module note documents, and grew to swallow the lower third of the window in a few frames. Position comes from the device (`platform::location`, `navigator.geolocation`) on the web and from the avatar everywhere else — there is no native provider, and `LocationWatch::available()` says so rather than inventing a fix. **The subscription is refcounted and shared**, because two resources own one receiver: `locate::LocateTracking` holds a watch while the ⌖ button is lit and `DriverState` holds one while driving, and driver mode makes locate stand down — so pressing Start used to drop a receiver warm for minutes and cold-start another, which is most of "Waiting for GPS…". `LocationWatch::start` joins the running provider when there is one; `platform::location::SHARED` is a `Weak`, so the radio still goes down when the last handle drops. On Android the watch also registers on **every** enabled provider rather than on `fused` alone (naming `gps` is what starts the acquisition at the moment the user pressed Start, instead of whenever the blend decides), and a cached first fix is published with its **accuracy widened by its age** (`stale_accuracy_m`) rather than refused: an old position shown as a *poor* one beats an arrow that has not appeared, and every consumer already reads `accuracy_m`. **Driver mode borrows the camera, and the autosave sees past it** — `DriverState::pose_before_drive`, the same trick `data_layers::sky_prefs` plays with the temporary clear sky. Without it a phone killed while driving came back next launch in Follow behind an avatar, having forgotten that the user was in Earth mode when they pressed Start. `--ui driver` seeds a route and arms the mode for a headless capture.
- **The ground is a measured field now, and everything that stands on it samples the same one** (`systems/map/terrain.rs`, `docs/notes/terrain-relief.md`). One AHN request per map anchor (6.4 km at 25 m) is baked into `TerrainField`; `at(wx, wz)` is a bilinear lookup that returns **0** when the layer is off, outside the Netherlands, or still fetching — so every consumer adds it unconditionally and the old flat behaviour is the same code path. Heights are **relative to the ground under the anchor** (absolute NAP would drop the world 322 m in Vaals for an identical picture) and the field **tapers to exactly zero at its own boundary**, or the measured ground meets the flat clipmap at a cliff that moves with the camera. Four things are non-obvious. **The field lands a second or two after the anchor it belongs to**, so every streamer builds its first cells flat and must rebuild on `TerrainField::revision` — surfaces, both building streamers, the marker cells and the route line all carry that revision and retear when it changes. **Earcut's two triangles cannot follow a hill**, so ground surfaces are refined first (`refine_for_terrain`), per *edge* rather than per triangle: a per-triangle rule leaves T-junctions where a split triangle meets an unsplit neighbour, and a T-junction on a slope is a crack. **Water, bridge decks and buildings take one height for the whole thing**, for two different reasons — a lake is level and a viaduct is straight, while a building's vertices are heights above its own base and displacing them individually racks the walls out of plumb. **The sim stays flat**: it holds no map data and never will, so the terrain is added on the display side (`AvatarState::display_position` = `position` + `terrain_lift`), and the lift is stripped before each reconciliation or prediction and correction fight for as long as you stand on a slope. Coarse clipmap levels get no relief geometry — they are *sunk* below the field's lowest point, because the pyramid stacks levels 0.4 m apart and an eight-metre hollow would otherwise fill with blurry z10 imagery from below. `--height` switches the layer on for a scripted capture (`terrain_ready` / `terrain_relief_m` in the metrics); over a Dutch city the relief is ~2 m and the picture barely changes, so check it on the Veluwe.
- **Water is two unrelated shaders, one per tier — and the local one is the only place a wave exists.** Local (`systems/map/water.rs`, `shaders/water.wgsl`): an `ExtendedMaterial<StandardMaterial, _>` over the vector surface meshes. Extending rather than replacing is the whole trick — the sun, shadow cascades, fog and the atmosphere's environment map already reach every standard material, so the sea reflects *this* sky through the day/night cycle for free. The polygons are flat (earcut on a canal emits two triangles), so every wave lives in the **normal**, never in a vertex. Three things are load-bearing: (1) the wave field is evaluated in **UV0 = metres from the map anchor**, not `world_position` — under `big_space` the origin jumps a whole grid cell as you move, which would snap the phase of the entire sea at once; (2) each octave carries its own **distance fade**, and the detail it drops is paid back as *roughness*, or a 20 cm ripple a kilometre out flickers as white noise under any camera motion; (3) sea state comes from `WeatherState`'s wind, and steepness/wavelength/speed/foam must move **together** — a longer wave at a lower steepness reads as a flat sheet. Whitecaps mask on *chop riding a big crest* (the product of the long and short octave bands); a threshold on total height paints continuous ribbons down every crest instead of spray.
- **Water's shore field is why it is the one surface group with a material per cell.** Earcut only ever emits the polygon's own boundary vertices, so a per-vertex distance-to-bank would be identically zero — the answer has to come from the shape's interior, i.e. a raster. `vector_tiles::water_shore_field` rasterises the water layers and runs an exact Felzenszwalb distance transform (seeded with a large *finite* value, never `∞`: the envelope subtracts one sample from another and `∞ − ∞` is a NaN that poisons a scanline). Distances are measured only against land **inside the tile** — that *is* the truth for the interior, since in MVT land is the absence of a water polygon, and padding the raster with a land border would draw a shoreline down the middle of every river that crosses a tile edge. That one number buys shelter (a 12 m canal never gets the open river's swell — the single most artificial thing flat water can do), a shallow tint, and a foam line that laps against the bank. It also means the shared-material rule the other groups follow cannot apply here, so the wind parameters live in `WaterSeaState` and new cells read them at spawn (same contract as `GlobeSurfaceAlbedo`).
- **Grass is generated in the vertex shader, not scattered — and it is the one layer here that does not stream** (`systems::grass`, `cartopolis_geo::turf`, `docs/notes/grass-is-generated-not-scattered.md`). Doing it the way the trees are done was measured and rejected: a legible lawn is ~10 blades/m², so the 26 m disc around the camera is ~20,000 of them ≈ 6 MB of vertex buffer that would be **rebuilt as the avatar walks**, i.e. the documented device-loss churn made continuous, which no per-frame cap removes. So nothing is stored: one shared 5-vertex-per-slot lattice mesh, one material, and a **fixed pool of patch entities** that slides along a world lattice — crossing a lattice line moves a `Transform` and rewrites a `MeshTag`, and after startup the layer uploads nothing. Existence and ground height come from a small moving `Rg8Unorm` mask (384², 96 m, 25 cm/texel) rasterised on a worker every twenty-odd metres. Four things are load-bearing. The blade hash must be keyed to the **anchor-metre frame reconstructed from `MeshTag`**, never `world_position` — under `big_space` the render origin jumps a grid cell and would reshuffle every blade at once (`water.wgsl`'s UV0 solves the same trap, and is unavailable here because the mesh is shared). That key is **quantised to millimetres**, or the last-bit difference between two patches' arithmetic puts a seam along every patch boundary. **Nothing in the layer is transparent and nothing may become so**: both the distance retire and the altitude fade are *height* ramps (a blade shrinks into the ground), which is why they compose without a seam. And it is a `MaterialExtension` with a **vertex shader only**, so the sun, shadows, fog and the atmosphere's environment map light a lawn exactly like the ground under it — the off-the-shelf Bevy grass crates are standalone `Material`s and would light it like a decal. Unverified: never run on a phone (it is behind `Budget::detail_layers`, so a handset starts with it off), and colour/lighting are not evidence on the container's software rasteriser — `grass_patches` / `grass_slots` in `--dump-state` are the geometry half that is.
- **The globe's ocean is a BRDF split, not water** (`systems/map/globe_ocean.rs`, ADR-025 tier). From orbit a wave is orders of magnitude below a pixel; what makes an ocean read as an ocean from space is that it is dark and glossy where land is matte, plus the sun's glint. So it is one mask per texel driving roughness/specular/tint on the globe's own tile materials, and it shares nothing with `water.wgsl`. The mask rides in the **alpha channel of the tile imagery** (opaque tiles, so alpha was free) — no extra texture, binding or upload, and the mip chain averages it so coastlines soften with distance instead of aliasing. Read it out of `pbr_input.material.base_color.a` **before** `alpha_discard`, which flattens alpha to 1 for an opaque material. The `has_mask` flag is not optional: an unbound base-colour texture samples as opaque white, so without it the backstop sphere (no imagery at all) turns the entire planet into ocean. Vector sources get an exact mask from geometry; raster ones are classified by `blue − red`, which separates map water and real sea from land where a hue test trips over the green end. Everything ramps on `space_factor` alongside the albedo — the flat map tiles below the boundary are matte and full-brightness, so anything arriving early is a step in the middle of a climb. `CARTO_NO_OCEAN=1` strips it for bisecting.
