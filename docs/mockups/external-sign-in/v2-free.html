The providers

  • Codeberg: run by a German non-profit association on Forgejo. Standard OpenID Connect, and it gives a verified e-mail address, so it behaves exactly like Google in v1.
  • Mastodon stands for the whole fediverse (Mastodon, and the many servers that copy its sign-in: GoToSocial, Pleroma, Akkoma…). There is no single server to send you to, so it asks which one first (section 2).
  • A community's own server (garage44 here): any OpenID server, with its name and logo set by the operator. A neighbourhood association, a school or a co-op that already runs Nextcloud, Keycloak or Forgejo can let its members in with the accounts they have.
  • Google and GitHub as in v1. Each one is still off until the operator configures it, so a server can offer only free ones, or none.

Why the grid

  • Five full-width buttons push the password form off a phone screen. Two columns keep every option the same size, so no provider looks like the default.

How it differs from Google

  • Cartopolis registers itself with each server the first time someone from it signs in (Mastodon's POST /api/v1/apps), and remembers that. The operator configures nothing for this one beyond turning it on.
  • No e-mail address: Mastodon's sign-in shares the account, not the address. So there's nothing to link on (v1 section 3 doesn't happen here), and the address is optional.
  • A bonus that fits Cartopolis: the fediverse handle shows as confirmed on your profile. The server already federates public posts (fediverse-live), so your followers can trust it's the same person.
  • Servers can be refused. The operator can block a server, using the same list it already uses for federation.

5Turning them on

Codeberg and a community server are one generic OpenID block each, so a new provider of that kind is configuration, never code. Mastodon is one switch.

# cartopolis.toml — listed in the order the buttons appear
[[auth.openid]]
name      = "Codeberg"
issuer    = "https://codeberg.org"
client_id = "…"           # secret from the environment

[auth.fediverse]
enabled   = true          # registers itself per server

[auth.google]             # as in v1
[auth.github]

[[auth.openid]]
name      = "garage44"
issuer    = "https://code.garage44.eu"
logo      = "garage44.svg"
client_id = "…"

Server side, on top of v1

  • Generic OpenID reads the issuer's discovery document, so Codeberg, Forgejo, Keycloak, Authentik, Nextcloud and Google itself all go through one path. GitHub and Mastodon are the two that need their own code.
  • The fediverse needs a table of registered servers (server, client id, secret), filled on first use and cleaned when a server stops answering.
  • Free providers can't be trusted more than Google. A community server's verified e-mail is only as good as that server. So linking to an existing account always asks for the password (v1 section 3), whoever the provider is.

Open questions

  2. Which free ones to switch on at launch? Drawn: Codeberg, Mastodon, and garage44's Forgejo as the example community server. Others worth a look: Disroot, a Nextcloud host.
  3. Fediverse: any server, or only an allowed list? Any server means anyone can stand one up and make accounts at will. That's no worse than the open sign-up form, but it skips the confirmation e-mail. Drawn: any server, minus the federation blocklist (fediverse_blocklists).
